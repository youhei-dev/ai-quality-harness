## 問いへの答え（レビュアーの結論の要約。実装者の評価ではない）

- **問い 1（R1 の 3 件）**: 3 件とも解消（上の表）
- **問い 2（ID の検出と fail open）**: 名前付きの参照の拒否、数値の参照の復元、HTML のコメント・タグを取り除く照合を確かめた。依頼の範囲で、新しい fail open の具体的な経路は特定できなかった。Markdown と HTML のすべての表示の解釈を再現しない制約は ADR-0026 に明記されており、再指摘の対象から外した
- **問い 3（`writeAtomic`）**: ランダムな名前・排他的な作成・開き直しの非追跡・rename・失敗時の削除を確かめた。通常の単独の実行で、前回のリンクの追跡と外のファイルの上書きが残る経路は無い。`writeReports` は引き続き `writeAtomic` を使い、履歴の名前の確保の後の失敗時の処理も保たれている。同時に一時ファイルを差し替える攻撃と、強制終了の残骸は既知の限界。書き込みの失敗時にほかの既存のレポートまで戻す仕組みではない点は、今回の変更による新しい問題ではない
- **問い 4（再取り込み）**: 保存済みのファイルの属性の検査と前の回の検査をどちらも行うので、前回の早期の成功の経路は解消。`--allow-missing-previous` が許すのは ENOENT の不在だけで、破損・不一致は成功にならない
- **問い 5（止め過ぎ）**: 文字参照の書き方をコードの例や説明の中で引用した正当なレビューも、禁止された名前を含めば止まる（R1 の原文が新しい版で止まることを回帰テストが示す）。ただし、人間が採った fail closed の仕様と、更新したひな形に合っており、記法を言葉での説明に変えられるので、不具合の指摘とはしない

**問い 5 への受け止め（実装者）**: 決めた仕様どおり。文字参照を引用すると止まるのは、人間の決定 1（名前付きの文字参照があれば止める。許すのは 5 つだけ）のとおりで、ひな形の出力の形 7 で「文字参照について説明するときも `&` と `;` を付けずに名前だけを書く」と頼んでいる。R2 の原文自身が、文字参照の扱いを論じながら名前付きの参照を 1 つも使わずに書かれ、そのまま取り込めた（この運用が成り立つことの 1 つの実例）。変えない
