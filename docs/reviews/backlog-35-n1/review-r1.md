## 問い1 — C2はすべての入力で旧正規表現と同じ置換になるか

**提示実装のコード分析上は、同じ置換になると判断する。**

- 旧式 `/(\b[a-z][a-z0-9+.-]*:\/\/)([^\s/:@]+):([^\s/@]+)@/gi` は、scheme の終端が `://` の直前で固定される。新実装は `indexOf("://")` で候補終端を探し、その左の scheme 許容文字列を後ろ向きに調べ、その中で `\b` と先頭英字条件を満たす最左位置を選んでいる。`\b` が参照する ASCII の `[A-Za-z0-9_]` と scheme 許容文字の差（特に `_`、`.`、`+`、`-`）もコードで明示的に区別している。
- 大文字小文字は、scheme 部分の `isLetter` とユーザー・パスワード部分の `/iy` で旧式の `/gi` と整合する。`u` フラグのない文字クラス・単語境界に関する前提も整合する。
- `URL_USER_PASSWORD` の sticky `y` は `sep + 3` だけで照合し、ユーザーの `:`・`/`・`@` の禁止、パスワードの空白・`/`・`@` の禁止、パスワード中の `:` を許す条件を旧式と同じ文字クラスで判定する。`\u{12}4` などの類似文字をASCII文字として誤認する実装にもなっていない。
- 成功時に `done` と探索開始位置を一致末尾へ進めるため、旧式の global 置換と同様、重複せず左から順に置換する。置換前に確定した接頭部分と `://` を維持し、認証情報だけを `"[REDACTED:url-credential]@"` にする。
- 新テストは旧正規表現を oracle として保持し、固定seedの入力40,000件、既存の等価性入力、連続一致・空白・記号・大小文字・長いschemeなどを比較している。ただしテスト結果そのものはパケットに含まれない。

## 問い2 — 最悪の入力で線形か

**`maskUrlCredentials` 単体について、入力長に対して線形と判断する。**

- `indexOf("://", from)` は探索開始位置 `from` を前進させる。後方の scheme 走査は `:` を横断できないため、別の `://` 候補に対して同じ長大な scheme 範囲を何度も逆走査しない。
- 有効な開始位置を探す前向き走査は、対応する候補の scheme 範囲内だけを調べる。認証情報の sticky 正規表現も、失敗時の探索は次の `://` に含まれる `/` を越えて継続できないため、候補同士で長大な部分文字列を再走査しない。成功時は末尾まで探索位置が進む。
- したがって、旧式のように一つの長い `a.a.a...` を多数の `\b` 位置から繰り返し走査する二乗時間の経路はない。出力文字列の連結は JavaScript エンジンの実装に依存するが、入力範囲の走査・コピーの設計上、同じ長大な入力区間を反復走査する箇所は見当たらない。
- 64 KiB／1,000 ms のテストはあるが、パケットには実測結果がない。**時間上限がすべての環境で保証されるという意味ではない。** また、他カテゴリの正規表現を含む `maskSecrets` 全体の最悪計算量まで、この修正だけから線形とは断定しない。

## 問い3 — 排他的履歴作成は命名規則、終了コード2、上書き防止を保つか

**命名規則と、通常の並行実行で他実行の履歴を上書きしない性質は、提示実装で確認できる。終了コード2への変換は未提示の呼び出し元の確認を要する。**

- `reserveHistoryPath` は `<stamp>.json`、`<stamp>-2.json`、`<stamp>-3.json` … の順に `openSync(candidate, "wx")` を試みる。既存の通常ファイル、ディレクトリ、シンボリックリンク（dangling を含む）は `EEXIST` として飛ばす。既存の命名規則を保っている。
- 別プロセスも同じ関数を使うと、同じ履歴名の排他的な新規作成は同時に成功できない。いったん取った名前にはこのプロセスの予約ファイルが残るため、通常の競合プロセスは次の名前を取る。`renameSync` は予約済みの自分の名前を置換し、別実行の履歴を置換しない。
- `openSync` の `EEXIST` 以外、`closeSync` の失敗、履歴 `writeAtomic` の失敗はいずれも再送出する。`closeSync` や `writeAtomic` に失敗した際は自分の予約ファイルの削除を試みる。削除自体が失敗したときは元の書き込みエラーを優先する。
- 競合を割り込ませるテストは別 Node プロセスで `writeReports()` を呼び、それぞれの履歴名・内容を検証する。名前の飛ばし方と `renameSync` 失敗時の後始末のテストもある。テスト結果は未添付。
