**実装者の確認**（コード。`src/runner/execute.ts`、v0.5.38）:
- `CONFIRM_POLL_MS`（25）は、`setTimeout(poll, …)`（エスカレーションの確認）と `setTimeout(watchAfterExit, …)`（leader の `exit` の後の確認）の遅延として使うだけ。`terminateActiveChildren` の `waitUntil` も `setTimeout(…, 50)` の遅延
- コールバックが実際に走る時刻に上限を設けるコードは無い。最初の確認は `child.on("exit")` のコールバックの中で始まる
- `groupAlive()` は signal 0 の成功で「ある」とするので、再利用された番号と自分のグループを区別できない。`gone` が立っていなければ、タイムアウト・中断の `killTree()` はその番号へ送る
- したがって、残る窓は「グループの消滅（または最後の確認）から、次の確認・送信が実際に走るまで」で、25 ms・50 ms は設定値（目安）であって上限ではない。v0.5.34 からの「最後の確認から送信までの 25 ms／50 ms」も同じ書き方だった

**実装者の補足（推定。レビューの「`exit` のコールバックの遅れ」の点）**: leader がグループの最後のメンバーの形では、leader が回収されるまでは番号が再利用されない（ADR-0023 の「範囲〈v0.5.35 で追記〉」の到達しやすさ: macOS で、回収の前は `kill(-pgid, 0)` が ESRCH にならないことを手元で確かめた）。Node は回収と同じコールバックで `exit` を出すので、この推定に立つと、`exit` のコールバックの遅れはその形の窓を広げない。窓を広げうるのは、leader の回収の後に最後のメンバーが消えたときの、タイマーのコールバックの遅れ。実測はしていない。どちらにしても、上限を主張しない書き方は同じなので、判定と対応は変わらない。

## 問いへの答え（レビュアーの結論の要約。実装者の評価ではない）

1. **28: ESRCH を見た番号へ 0 以外のシグナルを送る経路**: ESRCH を実際に観測して `gone` が立った後については問題なし。`watchAfterExit()` は `groupAlive()` だけを使い、エスカレーション・SIGKILL のタイマー・`poll`・`terminateActiveChildren`・abort は同じ `GroupState` を共有する。通常の終了で増えたのは signal 0 だけで、`goneAt`・待ちの起点と時間・終了コードは変わらない。確定の後にタイマーは残らない。pid なしと Windows では何もしない
2. **28: 閉じない範囲の説明**: 概念は正しいが、「25 ms 以内」という上限の書き方が強すぎる（B28-R1-001）
3. **5: 見張り役の `process.kill(0, "SIGKILL")`**: 自分のグループ以外に届く経路は、コードからは見つからない（起動時の先頭の確認、detached でない起動、stdin が最初から閉じている場合を含む）
4. **5: 止め方と後始末**: 問題なし（単独の SIGINT・SIGTERM、runner のグループへの SIGKILL、時間切れ。削除の対象の制限、削除の失敗でも止めること、終了コードは fail closed）
5. **既存テストの期待値の変更**: 不変条件を弱めていない（ESRCH の後に何も送らないことは、同じファイルの最初の 2 件と、28 の新しい 3 件が固定している）
6. **テストの質**: 28 と 5 の主要な契約をかなり直接に固定している。ただし 28 の 25 ms の上限は固定できておらず、そもそも実装がその保証を持たない（B28-R1-001）。5 の偽の vitest は、確かめたい性質を代表している
