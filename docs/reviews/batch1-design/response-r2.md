## 人間の決定（2026-10-22）

- **R2 の指摘への対応の方針**: 5 件すべてを受け入れ、次のとおり設計に反映する

  - 003（層 c）: 位置ごとの分類・除外の判断と、最後の finding の重複を除く鍵を別の仕様として書く。除いた数は出現した位置の数。finding は既存どおり「行番号＋符号位置」で 1 件（パス名は符号位置で 1 件）。同じ行に、除く U+200D と除かない U+200D が混ざるとき、除いた数は除いた位置の数、finding は 1 件。この混在をテストする
  - 004（47）: 読み手の約束を「`startedAt` が違えば確実に別の run。同じでも同じ run の保証はない」に直す。同じミリ秒の `startedAt` を持つ 2 本を使う 47-c-2 の変種のテストを足す（時計を固定するなどの既存のテストの手法で）。確実に見分けるには runId か history の一意の鍵が要ることを書き、ROADMAP の新しい項目の文案にする

- **B1-Q7 は B-1、B1-Q17 は A'、B1-Q25 は A、B1-Q5 は細部を含めて A'（確定）**。そのほかの Q は推奨どおり（仮決め。R3 の後に確定）

## 指摘ごとの対応

### B1-D-R2-001 — 窓から消える未決の候補（受け入れ）

- **指摘の要点**: R2 の I5 は「その窓では決めない」と「どの窓でも両端が見えないときは finding」を述べ、I6 は「両端が見える最初の窓で 1 回だけ決める」とする。`LineAssembler` は窓を渡した直後に保つ部分より前を捨てるので、その部分の候補が未決なら、次の窓ではその位置が無く、未検出になりうる
- **根拠の行**: 指摘は `src/security/scan.ts:502-515` を挙げるが、基準の commit で窓を渡して先頭を捨てる所は `:532-550`（`:535` の窓の渡し、`:536` の `floor`、`:538-542` の `from`、`:544` の `window.slice(from)`）。指摘の中身は、この位置のコードにそのまま当てはまる
- **対応**（設計 R3 の §4.5 の I5・I6、ADR-0037 の案 R3 の決定 3）
  - I5 を「窓の中での決め方」に書き直した。各窓で、候補を含む run ごとに、(a) 両端が見えれば I4 で決める、(b) その窓が行の最後の渡しである・run が窓の先頭に接する・左の隣が保証された末尾（次の窓の先頭に必ず入る最後の `lineOverlapBytes`）より前にある、のどれかなら、まだ決めていない候補をその窓で finding に確定する、(c) 残り（左の端が見え、右の端が窓の末尾に接し、左の隣から run の終わりまでが保証された末尾の中）だけを、その窓では決めない
  - 決めずに次の窓へ回せる長さは `lineOverlapBytes` で抑えられる（持ち越しの長さの上限）。左の隣を含めてそれ以上の長さの run が窓の境目にまたがれば、必ず finding
  - I6 を「1 回だけ決める・未決の候補を持ち越さない」に書き直した。未決の候補（位置・分類）を窓の外の状態として持たない。(c) の候補は、`LineAssembler` が次の窓の先頭に必ず入れる文字の中にあるので、次の窓でもう一度見る。持つ状態は「この行で決めた位置」だけ。行の最後の渡し（改行・ファイルの終わり）では (c) に当たらないので、決まらない候補は残らない
  - 直しの中で見つけた点: 層 (c) は走査を UTF-16 の単位から符号位置に変える（タグ文字はサロゲートの組）。保証された末尾の始まりは組の途中に来うるので、窓の先頭が組の後ろ半分だけのときは、その文字を「分からない」として run が窓の先頭に接するとみなす（E の外とみなすと、左の端を誤って確定しうる）。I5 の (b) に入れた
  - `LineAssembler` から生の文字の走査に渡すものに、届いていない窓の保証された末尾の始まり（`:536` の `floor` と同じ値）を足した（§4.7。秘密の形の走査は変えない）
- **テストの計画**（設計 R3 の §4.8 の L16 の (a)〜(g)）: (a) 持ち越しの長さの上限（`lineOverlapBytes` を 300 と 299 にして、境目がちょうどそこにあること）、(b) ファイルの終わり、(c) 改行、(d) 重なりの中の重複（保つ部分が重なりより長い窓で、前の窓で finding にした候補を決め直さない）、(e) サロゲートの組の分かれ目、(f) 窓の境目の前後のすべての位置に並びを置いて、もれも重複も無いこと、(g) 窓を何度もまたぐ
- **残したもの**: 指摘の修正案のもう 1 つ（未決の候補を保持して後から必ず決める）は、人間の決定のとおり採らない（ADR-0037 の案 R3 の代替案に理由を書いた）。窓の境目にまたがる長い run と、窓の先頭に接する run の候補は、正しい並びの内側でも finding になる（FAIL の向きの誤り。既知の限界）

### B1-D-R2-002 — 監視系のオプション（受け入れ）

- **指摘の要点**: 規則 7 の拒否は語 `--watch` と `--watch-path` だけで、`--watch-path=値` や `--watch=…` の綴りを確実に覆っていない。等号形を同じオプションと正規化する契約が無い。監視つきの check を available と提案すると、verify が終わらない恐れがある
- **対応**（設計 R3 の §2.4 の規則 4・5・7）
  - 規則 4: Node のオプションを左から読み、1 つずつ名前と値に正規化する（`--名前=値` の 1 語、一覧にある `--名前` と次の語、そのほかは名前だけ）。読むのをやめる所（`--`・スクリプトの名前・本文を取るオプション）は R2 のまま
  - 規則 5: 名前が `--test` で値の無いときだけ認める（`--test=…` は認めない）
  - 規則 7a: 実行位置より後ろの**すべての** `-` で始まる語（引用ありの語、スクリプトの位置・`--` の後ろの語も含む）を正規化し、名前に `watch` を含むものがあれば認めない
  - 規則 7b・7c: `NODE_OPTIONS=…` の前置き（中を読まない）と、別のファイルからオプションや環境を読む `--experimental-config-file`・`--experimental-default-config-file`・`--env-file`・`--env-file-if-exists` も認めない（init はそのファイルを読まないので、中で監視が入らないと言えない）
- **手元の `node --help` で確かめたこと**（Node v24.13.1。通信なし）: 監視に当たるオプションは `--watch`・`--watch-path=...`・`--watch-kill-signal=...`・`--watch-preserve-output` の 4 つ。`NODE_OPTIONS` で使える旗の一覧（`process.allowedNodeEnvironmentFlags`）には、ほかに `--no-watch`・`--no-watch-preserve-output` がある。値を別の語で取るオプションの固定の一覧（R2 の 18）は、どれも help で値を取る形だった
- **テストの計画**（設計 R3 の §2.6）: N2c（正規化で同じに読まれる形を認める）、N5i（`--test --watch-path=src`・`--watch-path=src --test`・2 語の形・値なし・`=` の後ろが空・`--watch=true` など）、N5l（ほかの監視の名前、`--no-watch`、引用ありの語、スクリプトの位置・`--` の後ろ）、N5m（`NODE_OPTIONS`・設定のファイル・環境のファイル）、N5n（`--test=1`）
- **残したもの**: どれも「検出しない」向きで、unit は今と同じ NOT APPLICABLE（手で足す）。verify を走らせる環境の `NODE_OPTIONS` や npm の設定が足すオプションは、init からは見えない（§2.8）。監視のモードで動いた check は、check の `timeoutSec` で止まって FAIL になる（`src/runner/run-checks.ts:104`）

### B1-D-R2-003 — 位置の判断と finding の鍵（受け入れ）

- **指摘の要点**: 既存の「同じファイル・行・符号位置で 1 件」の集約と、R2 の「候補の位置ごとに 1 回決める」を区別していないので、除いた数と finding の数の仕様が曖昧
- **根拠の行**: 指摘は `src/security/scan.ts:384-412` を挙げるが、基準の commit で `RawCharSink` は `:408-426`（`seen` は `:410`、鍵 `${no}:${cp}` は `:420-421`）、パス名の走査 `checkPathName` は `:429-439`（鍵は符号位置、`:430-435`）。指摘の中身は、この位置のコードにそのまま当てはまる
- **対応**（設計 R3 の §4.5 の I9、ADR-0037 の案 R3 の決定 2・3）
  - 位置の判断: 走査する文字の出現ごとに「除く」か「finding の側」を 1 つ決める。「除く」は I1 の候補が I4 に当たるときだけ
  - 除いた数: 「除く」の出現の位置の数
  - finding の鍵: ADR-0036 の決定 2 のまま（中身は「ファイル・行番号・符号位置」、パス名は「パス・符号位置」）。その鍵の出現に「finding の側」が 1 つでもあれば 1 件。「除く」の出現は finding を作らず、消しもしない
  - 例（指摘の例そのもの）: 同じ行に、RGI の並びの中の U+200D が 2 つと、並びの外の U+200D が 1 つ → 除いた数 2、finding 1
  - `security.allow` は finding だけに効き、除いた数を変えない
- **テストの計画**（設計 R3 の §4.8 の L24）: 同じ行の混在（順を入れ替えても同じ）、並びの外が 2 つ、並びだけが 2 つ、パス名の混在、長い行で並びが重なりに入る形、allow で抑えたときの除いた数
- **残したもの**: 無し（finding の数え方は変えない）

### B1-D-R2-004 — `startedAt` の読み手の約束（受け入れ）

- **指摘の要点**: `startedAt` はミリ秒の ISO の表記で、history の名前は秒に丸めて衝突時に連番、run の一意の ID は無い。同じミリ秒に始めた別の run は同じ `startedAt` を持てるので、文字列の一致だけで「同じ run」と断定する約束は成り立たない
- **対応**（設計 R3 の §6.4）
  - 約束 3 を「違えば確実に別の run。同じでも同じ run の保証はない」に直した（R2 の「同じなら同じ run」は誤りだった）
  - 約束 4 (b) に、同じ `startedAt` の history が 2 つ以上あれば、どれが `latest.json` の run かは決められないことを足した。確実なのは (c) の「並行の無い状態でやり直す」だけ
  - 約束 6 を足した: 確実に見分けるには、runId か history の一意の鍵を `latest.json`・`latest.md`・history に同じ値で書く仕組みが要る。今は無い
- **テストの計画**（設計 R3 の §6.6 の 47-c-3）: 47-c-2 の変種。run A と B に同じミリ秒の `startedAt` を与える（前例 `tests/regression-rest2-n1-history-name-race.test.ts:47-57` と同じく、`buildReport` に `startedAt: new Date("…")` を渡して時計を固定する）。差し込みで `latest.json` が B、`latest.md` が A になっても、約束 3 の照らしは「違うとは言えない」と判定し、`history/` の 2 つの候補を `startedAt` だけでは決められないことを固定する（見分けの印には、テストの中だけで違う `project.name` を使う）

### B1-D-R2-005 — 上限に近い遅さの記録（受け入れ）

- **指摘の要点**: run-checks は stderr の末尾を 200 行・64 KiB に切るので、reporter が多数の警告を出せば先の警告が落ちる。vitest 5 の reporter で各テストの有効な timeout が取れるかは、設計自身が未確認としている。判定を変えない選択は妥当だが、記録の完全性を断定できない
- **対応**（設計 R3 の §5.5）
  - SP3 で、vitest 5.0.0 の配布物の型定義と実装を読んだ（実行はしていない）。`Reporter` の `onTestCaseResult(testCase)` と `onTestRunEnd(…)`、`testCase.options.timeout`（型 `number | undefined`）、`testCase.diagnostic()` の `duration`（ミリ秒）がある。実装では `options.timeout` は `task.timeout` で、`task.timeout` はテストを集めるときに `options.timeout ?? runner.config.testTimeout` で決まり、同じ値がテストの時計に渡される。読んだ範囲では有効な上限が取れる見込み
  - **SP4 の最初に確かめる**: (1) その値が主の process の reporter にそのまま届き、テストの時計と同じか（設定の既定・テストの数の引数・`describe` の options）、(2) `duration` に hook の時間が入るか、(3) skip・失敗・時間切れのテストで何が見えるか、(4) reporter の stderr の行が `npm run test` の子の stderr にそのまま出るか
  - **取れない場合の振る舞い**: 個々のテストで上限が正の有限の数でなければ、一覧に出さず `unknown-limit` に数える。SP4 で、上限がテストの時計と違う、またはどのテストでも取れないと分かったら、v0.13.2 では reporter を入れない（上限の表を別に持つ形は、テストの中の上限と食い違っても気づけないので採らない）
  - **出し方**: 50% を超えたテストを割合の大きい順に最大 20 行（1 行は 300 バイトまで）。最後の 1 行はいつも件数（`over-half`・`shown`・`omitted`・`unknown-limit`・テストの数）。reporter の出力は最大 21 行・約 6.2 KiB で、verify が残す stderr の末尾（読むときに末尾の 10 MiB、レポートには 200 行・64 KiB）より小さいので、reporter の出力がどれだけ多くても件数の行は残る
- **テストの計画**（設計 R3 の §5.7）: 25 件・0 件・上限の分からないテスト・長い名前・最後の行がいつも最後・verify の `tail` を通しても件数の行が残ること
- **残したもの**: reporter の後に vitest や npm が 200 行・64 KiB に近い量を stderr に書けば、件数の行も落ちうる（ふつうは数行。判定は変わらず、`outputTruncated` が立つ）。check が時間切れ・中断で止まったときは何も出ない（check は FAIL か SKIPPED）
