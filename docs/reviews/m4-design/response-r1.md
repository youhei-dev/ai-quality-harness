## 指摘ごとの対応

### M4-D-R1-001 — 読み取り量の上限（受け入れ）

- **指摘の要点**: `fstat` で大きさを確かめた後の読み取り量に、独立した上限が無い。確かめた後に追記されると、8 MiB・256 MiB の想定を超えうる
- **対応**（設計 R2 の ADR-0034 の C の 1・D）
  - 事前の `fstat` の大きさに頼らない。開いた記述子から `readSync` をくり返し、最大で 8,388,609 バイト（上限 + 1）までだけを読む
  - 読んだ量が上限を超えたら `too-large`（読んでいる間に大きくなった場合も同じ）
  - 上限以下なら、読む前の `fstat` の大きさ・読んだ量・読んだ後の `fstat` の大きさを比べ、違えば `unreadable`（`code` は固定の語 `size-changed`）
  - 新しい分類を作らない理由: aiqh 自身は history を一時ファイル → rename で書き（`src/report/write.ts:100-109`）、その場で追記も切り詰めもしない。大きさが変わるのは外の何かが書いたときだけで、利用者のすることは `unreadable` と同じ（確かめて読み直す）。分類は利用者のすることで分けている
  - 全体の 256 MiB は、実際に読んだバイト数の合計（`too-large` の上限 + 1 バイトを含む）で確かめ、超えた時点で読むのをやめて入力の誤り（`HISTORY ERROR (too-many-bytes)`、exit 2、集計を出さない。Q4）
  - 検出しないもの（既知の限界に書いた）: 読んでいる間に、同じ大きさのまま中身を書き換えた場合
- **テストの計画**（ADR-0034 の M）: 上限 + 100 バイト、上限ちょうど・上限 + 1 の境界、追記の競合、切り詰めの競合、読んでいる間の増大、全体の上限（小さく差し替えて）。差し替えは、`src/parse/read.ts:23` と同じ「テストのための引数（設定・CLI からは届かない）」で行う

### M4-D-R1-002 — 祖先のディレクトリの差し替え（一部受け入れ）

- **指摘の要点**: realpath で包含を確かめた後、履歴のファイルを開くまでの間に、祖先のディレクトリを差し替えられると、確かめた場所と開く場所が一致しないおそれがある。修正案は、ディレクトリの記述子を基準にした探索、それができなければ脅威モデルの明示的な制限（再確認だけで完全な対策とは説明しない）
- **修正案の前半（記述子を基準にした探索）はできない**: Node の `fs` には、ディレクトリの記述子を基準に子を開く API（POSIX の `openat` の類）が無い
  - Node v24.13.1 の fs の文書（https://nodejs.org/docs/v24.13.1/api/fs.html ）: `fs.open()`・`fs.openSync()`・`fsPromises.open()` の `path` は `<string> | <Buffer> | <URL>` だけ。`fs.Dir`（https://nodejs.org/docs/v24.13.1/api/fs.html#class-fsdir ）のメソッドは `close`・`read`・`path`・反復などで、子を開くものは無い。`FileHandle` のメソッドも、その記述子そのものを扱うものだけ。頁の全文に `openat`・`AT_FDCWD`・`O_PATH` の語は無い
  - 手元の Node 24.13.1 でも、`fs.constants` に `AT_` で始まる定数と `O_PATH` は無く、`fs.Dir` の prototype にも子を開くメソッドは無かった
  - ネイティブのアドオンや依存の追加は、依存を最小にする方針（ADR-0008）に反するので採らない
- **後半（脅威モデルの明示的な制限）として扱う**（設計 R2 の ADR-0034 の脅威モデル・B の 7）
  - 脅威モデル: `aiqh history` は、利用者が自分の手元の自分のディレクトリを読む道具。読んでいる最中に、ほかの者がディレクトリを差し替える場面は対象の外。信頼しないのは、履歴のファイルの中身
  - やること（**検出**。防止ではない）: 初めに realpath で解決したパスを基準に列挙と open を行う。読み始める前と、すべてを読み終わった後に、history のディレクトリ（ルートを渡されたときは、ルート・`artifacts`・`artifacts/verification` も）を lstat し、種類・`dev`・`ino` が同じかを確かめる。違えば入力の誤り（`HISTORY ERROR (directory-changed)`、exit 2、集計を出さない）
  - 検出しないもの（既知の限界に書いた）: 読んでいる間に差し替えて、読み終わる前に戻した場合
  - lstat の後に symlink に差し替えられ、open が `ELOOP` で失敗したときは `not-regular` にする（B の 5）
- **テストの計画**（ADR-0034 の M）: すべてを読み終わった後に、history のディレクトリを移して別のものを置く（(b) の形）、`artifacts` を移して別のものを置く・`verification` を symlink に置き換える（(a) の形の祖先）、差し替えない対照、比べる関数の単体のテスト

### M4-D-R1-003 — 自由な文字列の長さ（受け入れ）

- **指摘の要点**: 許可リストに載る自由な文字列（`project.name`・`checks[].name`・`tool.version`）の長さを、マスクに渡す前に制限していない。極端に長い文字列が `maskSecrets` に入り、項目 40 の超線形を誘発しうる
- **対応**（設計 R2 の ADR-0034 の C の 5・C の 8）
  - zod の段で、`project.name`・`checks[].name` は UTF-8 で 256 バイト、`tool.version` は 64 バイト、1 run の `checks` は 256 個まで
  - 超えたら切り詰めずに `bad-shape`。その値は `maskSecrets` にも渡さない（マスクの前に切り詰めると、秘密の形が崩れた断片が残るおそれがあるため）
  - 表示の長さ（200 文字・64 文字）は、マスクの後に切る表の幅の上限で、入力の上限とは目的が違う。マスクは文字列を長くすることがある（URL の認証情報の形。手元で確かめた）ので、表示の長さは入力の上限と別に残す
  - 項目 40（`docs/ROADMAP.md:800`）との関係: `aiqh history` がマスクに渡す文字列は 256 バイト以下になる。項目 40 の実測は 64 KiB〜1 MiB での値
  - 設定は、長さ・数の上限の無い名前と checks を許す（`src/config/schema.ts:13-15, 63, 77`）。その差は新しい論点 Q11 にした
- **テストの計画**（ADR-0034 の M）: 256 / 257 バイトの境界（多バイトの文字を含む）、64 / 65 バイト、256 / 257 個、上限を超えた値がマスクに渡らないこと、8 MiB 近い 1 ファイルでの負荷（時間は assert しない。項目 41 の教訓）

### M4-D-R1-004 — HTML と JSON の数の照合（受け入れ）

- **指摘の要点**: 「数の葉のすべて」と HTML の `data-k` の完全一致を求めるが、どの値をどの要素に出すかが定義されていない。出さない数の許可リストも無い。SVG は検証の対象外になっている
- **対応**（設計 R2 の ADR-0035 の決定 6、ADR-0034 の G）
  - `data-k` の作り方: 集計の JSON の根からのキーと配列の添字を `.` でつないだパス（例: `projects.0.checks.3.durationMs.median`）。JSON のオブジェクトのキーはすべて固定の語にした（ADR-0034 の G）ので、パスは値を含まず、一意になる
  - **対応表**（JSON のパス → HTML の表示先）を 12 行で明文にした
  - **照合しない数の許可リスト**: `schemaVersion`（出さない）、`sources.*.index`・`unread.*.source`・`projects.*.sources.*`（識別子として札 `#<番号>` で出す）、`projects.*.checks.*.timeoutSec`（出さない）
  - 数の表示は `String(n)`、`null` は `-`。割合は JSON の段で小数 4 桁に丸め、HTML と同じ文字列にした
  - テスト: (1) `data-k` の重複が無い、(2) 対応表のすべてが HTML にあり値が同じ、(3) 許可リストの外の数が HTML に無い（JSON のすべての数の葉が対応表か許可リストのどちらか 1 つに当たる・`data-k` が許可リストに当たらない・出さない数の目印が HTML に無い）、(4) SVG、(5) 札の並び
  - 完了条件（§4.2・ROADMAP の文の案）の「完全一致」を「対応表のとおりに一致し、出さない数は許可リストにある」に直した
  - **SVG**: SVG の `<text>`・`<title>` と属性も、同じ出口 `h()` を通す。SVG の文字に数を入れない（数は表の `data-k` の要素だけ）。図形の大きさ（座標・高さ）は、表の数を画素にした値で丸めを含むので照合しない。照合するのは図の点の数（各 `<svg>` の `data-chart` が指す配列の長さ）

## 問いへの答え（レビュアーの結論の要約。実装者の評価ではない）

- **問い 1（信頼しない JSON）**: 指摘あり（001・002）。8 MiB・10,000 件・256 MiB は現時点で妥当な初期の上限。深さの上限を別に設けない判断は、読む欄の中の入れ子を含む負荷の試験を条件に容認。8 つの分類は通常の読み取りの失敗を覆うが、競合による読み取り量の異常の扱いを定義すること
- **問い 2（出さない欄）**: 指摘あり（003 と言い回し）。読まない欄を zod で捨てる方針は適切。実際の漏えいが生じた事実は確認していない
- **問い 3（HTML）**: 指摘あり（004）。固定のひな形・値のエスケープ・script 無し・CSS のハッシュ付きの CSP の方針は妥当。`writeAtomic` の `html` の追加に、設計上の明白な反対は無い。SVG のテキスト・属性にも同じ出口を使うことをテストすること
- **問い 4（fail closed）**: 指摘なし。読めない履歴なら集計を出して exit 2、入力そのものが不適切なら集計を出さずに exit 2、過去の FAILED は exit 1 を意味しない、の区別は妥当。競合で上限を超えたときは入力の誤りとして仕様に足すこと
- **問い 5（設定のハッシュ）**: 指摘なし。省略と `null` の区別、同じ `Buffer` からハッシュと文字列を作る方針、既存のテスト 2 か所の更新の計画は妥当。実コードを見ていないため、網羅の最終の保証ではない
- **問い 6（DB と R-010）**: 指摘なし。再検討の条件は具体的で、R-010 を ROADMAP の項目 47 に残す計画も妥当。後の PR で実際に反映されたことを確かめること
