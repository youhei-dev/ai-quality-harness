# M4 設計 R1 — 独立レビュー結果

対象: 添付の設計案とレビュー依頼。コード本体は未添付であり、コード実装・実行確認は行っていない。

### M4-D-R1-001

- ID: M4-D-R1-001
- 重要度: Medium
- 種別: 設計
- 対象: ADR-0034 の B の 5・C の 1・D
- 内容: ファイルの大きさを fstat で確認した後の読み取り量に、独立した上限が定義されていない。
- 根拠: B の 5 は open 後の fstat を指定するが、C の 1 は事前のサイズ確認だけ、D は lstat の大きさで合計するとしている。検査後に通常ファイルが追記・変更されると、読み込み量が 8 MiB や全体 256 MiB の想定を超え得る。
- 修正案: 記述子から最大 8 MiB + 1 バイトだけを読むこと、読み取り中のサイズ変化をどう分類するかを定義する。全体も実読バイト数で上限を再検査し、超過時は部分集計を出さない。追記・切り詰めの競合テストを足す。
- 確度: 推測

### M4-D-R1-002

- ID: M4-D-R1-002
- 重要度: Medium
- 種別: 設計
- 対象: ADR-0034 の B の 1・2・5
- 内容: ルート包含の realpath 確認と、後続の履歴ファイルを開く操作の間に、祖先ディレクトリの差し替えへの対策がない。
- 根拠: B の 2 は事前の realpath による包含を指定するが、B の 5 の O_NOFOLLOW は最終要素の symlink しか拒否しない。artifacts や verification などの祖先要素を検査後に置き換えられる環境では、検査した場所と実際に開く場所が一致しない可能性がある。
- 修正案: ディレクトリ記述子を基準に列挙と子の open を行い、祖先と対象を同じ探索の中で拘束する。環境制約で不可能なら、競合を脅威モデルの明示的な制限とし、再確認だけで完全対策とは説明しない。ディレクトリ差し替えのテストを追加する。
- 確度: 推測

### M4-D-R1-003

- ID: M4-D-R1-003
- 重要度: Medium
- 種別: 設計
- 対象: ADR-0034 の C の 5・F、ADR-0035 の決定 4
- 内容: 許可リストに載る自由文字列の長さを、マスク処理へ渡す前に制限していない。
- 根拠: C の 5 では project.name・checks[].name・tool.version は長さに上限のない文字列である。F はマスクしてから 200／64 文字に切る。8 MiB の JSON から作られた極端に長い文字列が maskSecrets に入り、§4.4 の項目 40 で認める private-key パターンの超線形処理を誘発し得る。
- 修正案: 入力の段階で自由文字列の最大バイト長・件数を設け、超過時を bad-shape とするか、安全な境界で処理を打ち切る仕様を決める。マスク前切り詰めによる秘密の断片露出を避けるため、単純な先頭切り詰めだけに依存しない。長い名前・版の負荷試験を追加する。
- 確度: 確認済み

### M4-D-R1-004

- ID: M4-D-R1-004
- 重要度: Medium
- 種別: テスト
- 対象: ADR-0035 の決定 6、§4.2
- 内容: JSON の「数の葉のすべて」と HTML の data-k の完全一致を要求するが、どの値をどの要素に表示するかが定義されていない。
- 根拠: ADR-0034 の G の JSON には sources の index・各種件数・check の timeoutSec・unknownRuns 等、多数の数値がある。一方 ADR-0035 の決定 6 は HTML のすべての数が data-k を持つとするだけで、各数値葉を表示する網羅的な対応表はない。SVG は検証対象外と明記されている。
- 修正案: JSON の数値葉から HTML の表示先への対応表と、配列添字を含む一意な data-k の生成規則を明文化する。表示しないメタデータ数値があるなら対象から除く許可リストを明示し、完全一致という完了条件の語をそれに合わせて修正する。重複キーと欠落を検出するテストにする。
- 確度: 確認済み

## 全体の結論

件数: High 0 / Medium 4 / Low 1

High はないが Medium が 4 件あるため、現状の設計 R1 は修正して再評価するのが適切。DB を持たず読み取り専用とする方針、設定ハッシュを変更記録に限定する説明、読めない履歴を列挙して exit 2 とする基本方針は妥当。

**問い 1〜7 への答え**

1. 信頼しない JSON: 指摘あり。事前サイズ検査後の読み込み量、祖先ディレクトリの競合対策を補う。8 MiB／10,000 件／256 MiB の値自体は現時点で妥当な初期上限。深さ制限を別に設けない判断は、既知フィールドに現れるネストを含む負荷試験を条件に容認。8 分類は通常の読み取り失敗を覆うが、競合による読み取り量異常の扱いを定義する。
2. 出さない欄: 指摘あり。読まない欄を zod で捨てる方針は適切。ただし JSON.parse の時点では元データは一時的にメモリに存在するので「メモリに残さない」は解析後の保持についての表現にする。自由文字列に上限が必要。実際の漏えいが生じた事実は確認していない。
3. HTML: 指摘あり。固定ひな形、値のエスケープ、script 無し、CSS ハッシュ付き CSP の方針は妥当。writeAtomic の html 追加にも設計上の明白な反対はない。SVG のテキスト・属性にも同じ出口を適用することをテストする。数値一致の網羅範囲を確定する。
4. fail closed: 指摘なし。読めない履歴なら集計を出して exit 2、入力自体が不適切なら集計を出さず exit 2、過去の FAILED は exit 1 を意味しない、という区別は妥当。競合で上限超過した際は入力エラー扱いとして仕様に足す。
5. 設定ハッシュ: 指摘なし。省略と null の区別、同じ Buffer からハッシュと文字列を作る方針、既存テスト 2 か所の更新計画は妥当。実コードを見ていないため網羅性の最終保証ではない。
6. DB と R-010: 指摘なし。DB 再検討条件は具体的で、R-010 を ROADMAP 項目 47 に残す計画も妥当。後続 PR で実際に反映されたことを確認する。
7. 完了条件・版・Q1〜Q9: 指摘あり。数値照合の検証可能性と Q1 の ADR 注記への紐付けを修正する。機能別の minor 版の順番と PR 分割には異論なし。Q1〜Q9 の推奨そのものに反対はない。
