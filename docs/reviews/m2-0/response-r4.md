**レビュアーが挙げていない形（追加で確認）**: key-value は、窓の末尾に達した一致の値が途中で切れると、値の判定（`looksLikeSecretValue`）が
切れた値に対して行われる。値全体ならコードらしさ（`()` 等）やプレースホルダ語で候補から外れるものが、切れた部分だけでは秘密らしく見えて finding になる。
正規表現の境界ではなく「値の判定に必要な右の文脈」が失われる形で、右の文脈の対策（確定の遅延）の対象に含める必要がある。

### 修正時に必要なテスト（M2-1 以降で追加する。修正前 FAIL を記録すること）

1. 左の文脈: 上の表の左側の各分類について、単語文字（key-value は英数字）+ 秘密の形を置き、秘密の形の先頭を次の窓の先頭に合わせる。窓なしで finding なし（ガード）、窓ありでも finding なし
2. 右の文脈: aws（直後に小文字）、github classic（直後に `_`）、google（直後に単語文字）を最初の窓の末尾ちょうどに置き、続きの文字を次のチャンクに置く。窓なし・窓ありとも finding なし
3. key-value の値の判定: 裸の値・引用値が窓の末尾で切れ、続きの部分で候補から外れる形（コードらしさ、プレースホルダ語）。窓なし・窓ありとも finding なし
4. 対照（ガード）: private-key と、続きの文字を本体が取り込む分類（github pat / gitlab / jwt）は、窓ありでも窓なしと同じ finding
5. **双方向の性質テスト**: 既存の「窓なし ⊆ 窓あり ∪ oversized」（見逃し防止）に加え、「窓ありの secret finding ⊆ 窓なしの finding」（誤検出防止）を、
   上限から導いた長さ・位置の生成器（R3 と同じ選び方）と、境界の直前・直後に単語文字 / 非単語文字を置く生成で確かめる
6. 既存の窓走査テスト（M2-0-001、M2-0-008、R1-001 の 3 層、R2-001、R3-001）がすべて通ること
