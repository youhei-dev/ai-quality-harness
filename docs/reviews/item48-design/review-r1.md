# 独立設計レビュー: item48-design / R1

対象は item48-design-r1.md と adr-0036-draft.md です。依頼文に従い、添付された設計と ADR 案を照合しました。以下の指摘は設計文書とテスト計画に対するもので、未実装のコードに不具合が存在すると断定するものではありません。

## 指摘

### I48-D-R1-001

- ID: I48-D-R1-001
- 重要度: Medium
- 種別: 文書
- 対象: 設計 §6-4、§9 の ADR-0028 注記・CHANGELOG 案、ADR の決定 10・代替案
- 内容: 新しい verify と古い security-scan の組合せまで「表示だけ」と説明すると、項目 48 の検出が有効になっていない状態を、導入済みと受け取らせます。パース失敗自体が合否に影響しないことと、子 scanner の版によって検出能力が異なることを分けて説明する必要があります。
- 根拠: 設計 §1 は旧 scanner が対象文字を検査しないとし、§6-4 は新 verify と旧 scanner の組合せで unexpected-summary になっても合否を変えないとしています。他の finding がない通常の追跡 UTF-8 ファイルに U+202E だけを加えた場合、この組合せでは旧 scanner が exit 0 を返し、check は PASS のままです。同じ入力を新 scanner で走査すれば、H4・ADR の決定 3 により exit 1、FAIL になります。これは設計書に記載された挙動から導く反例であり、実プロセスを動かした観測ではありません。
- 修正案: 新形式だけを受け付ける H8 と、パーサが判定に介入しない P1 は維持してください。そのうえで「パース失敗自体は判定を変えない。検出範囲は実際に起動する security-scan の版で決まり、新 verify と旧 scanner の組合せでは項目 48 の検出は有効にならない」と明記し、更新時には実際の子 scanner の版・commit も揃える案内を、設計・ADR・CHANGELOG に反映してください。
- 確度: 確認済み

### I48-D-R1-002

- ID: I48-D-R1-002
- 重要度: Medium
- 種別: テスト
- 対象: 設計 §8-1 T8。対応する契約は §5-2・§5-4、ADR の決定 8
- 内容: T8 は規則の条件を個別に列挙していますが、既存の分類なし規則と新しい分類明示規則を同時に置く場合の期待値がありません。個別条件の試験だけでは、実際に採用する規則自身が分類を明示していることと、正しい規則へ使用回数が付くことを保証できません。
- 根拠: 設計 §5-2 は raw-char の候補となる規則自身に分類一致を求めています。しかし、仮に「同じ分類の規則が設定内に一つでもあれば、既存の規則検索を実行する」という誤実装でも、単独規則で行う T8 の各条件は満たせます。先頭に分類なしの path: "tests/**"、後ろに category: "bidi-control" と path: "docs/approved.txt" の規則があると、この誤実装は tests/new.ts の U+202E を先頭の規則で抑えてしまいます。逆に、最初の一致規則を選んだ後で分類を検査して捨てる実装では、後ろにある正しい明示規則まで検索せず誤 FAIL にできます。指摘対象は、この組合せを明記していないテスト計画であり、現存する実装の欠陥ではありません。
- 修正案: T8 に、分類なし規則を先に置き、後続の分類明示規則が同じパスに有効に一致する場合、別パスにだけ一致する場合、期限切れの場合を追加してください。前者では正しい明示規則だけが raw finding を抑え、後二者では分類なし規則へ代替して抑えないことを確認します。同じファイルの secret と raw finding を混在させ、secret だけを汎用規則で抑えるケースも使って、suppressed・allowUsage・未使用・期限切れの記録が対応することを確かめてください。規則選択の契約は findAllowRule の直接テストでも固定すると明確です。
- 確度: 確認済み

### I48-D-R1-003

- ID: I48-D-R1-003
- 重要度: Medium
- 種別: テスト
- 対象: 設計 §8-1 T5・T6・T7。対応する走査範囲は §3-4、ADR の決定 5
- 内容: 「中身を読まないものも含め、列挙された全パスを検査する」という新しい境界が、パス名のテストで守られていません。T7 は追跡された通常ファイルの名前を対象とし、T5・T6 は主に中身の走査・除外を確かめています。
- 根拠: 設計 §3-4 は、二つの一覧に出た symlink・submodule・未追跡の .env*・作業ツリーにないものもパス名の検査対象としています。ところが、パス名の検査を通常ファイルの確認後、またはバイナリ除外後へ誤って置く実装でも、通常ファイルを使う T7 と、名前に対象文字を置かない T5・T6 は通せます。この配置では、中身を読まない対象の名前に U+202E があっても finding が出ません。列挙と内容走査を分離する要件は文書で確認できますが、その境界を検証するケースは T1〜T14 に明記されていません。
- 修正案: T7 に、未追跡で ignore されない通常ファイルに加え、バイナリ、未追跡の .env*、symlink、submodule、作業ツリーから消えた追跡パスの名前を検査するケースを追加してください。各対象の名前に対象文字を置き、内容を読まなくても line・endLine のない raw-char finding が出ることを確認します。未追跡で ignore されたパスは対象外であることも区別してください。必要な変更はパス名検査の試験であり、内容の走査対象を広げる必要はありません。
- 確度: 確認済み

### I48-D-R1-004

- ID: I48-D-R1-004
- 重要度: Low
- 種別: テスト
- 対象: 設計 §8-1 T5 の旧 commit における FAIL / PASS の見込み
- 内容: T5 の「前の 2 つは FAIL、最後は PASS」は、ignore による除外を維持するケースの期待と合いません。ignore された未追跡ファイルに finding がないことは、変更前から成立するため PASS です。
- 根拠: 設計 §3-1 のファイル集合は、追跡ファイルと、未追跡で ignore されないファイルです。T5 の三つのケースを順に読むと、新しい検出を必要とするのは最初の「未追跡で ignore されないファイルの文字 → finding」だけです。「ignore されたファイル → なし」を未追跡ファイルの意味で読むなら、後二つは既存の除外を維持する試験です。なお、追跡済みのファイルを意味するなら、ignore 指定があっても走査対象なので、「なし」という期待自体が不適切です。
- 修正案: T5 の ignore ケースが未追跡ファイルであることを明示し、変更前の見込みを、順に「FAIL / PASS / PASS」へ訂正してください。新しい検出を確かめる試験と、既存の除外を壊さない試験を個別に判定できる形にしてください。
- 確度: 確認済み

### I48-D-R1-005

- ID: I48-D-R1-005
- 重要度: Low
- 種別: 文書
- 対象: 設計 §11 の「言語ごとの字句解析を持たない」の説明
- 内容: 「閉じた（害の無い）並び」という表現は、開始と終端の対応が取れていれば安全だと読めます。閉じていることだけでは、表示による偽装の危険がないとは判断できません。
- 根拠: 同じ物理行で、最初のコメント内の U+202E を、実行文を挟んだ別のコメント内の U+202C で閉じる構成では、開始と終端は対応していても、その効果は複数の字句要素をまたぎ得ます。UTS #55 §4.1.1 は字句の境界を表示単位である atom の境界とし、§5.1.6 は効果が atom をまたぐことを警告の観点としています。資料: [UTS #55](https://www.unicode.org/reports/tr55/)。今回の設計は閉じた並びも検出するため、検出方針の欠陥ではなく、安全性の説明の問題です。
- 修正案: 「閉じた並びや正当な利用も含めて finding にする。開始と終端の対応だけでは安全性を判断しない。正当な利用は allow で扱う」という説明に改めてください。検出方針の変更は不要です。
- 確度: 確認済み

## 全体の結論

件数: High 0 / Medium 3 / Low 2

**High はありません。Medium が 3 件あるため、現案のままでは設計レビュー完了とはしません。** 版の食い違いについての説明を修正し、複数の allow 規則と、中身を読まない対象のパス名について、テスト計画を補う必要があります。

11 文字に限定すること、既定で FAIL とすること、分類を明示した規則だけで抑えること、scanString とファイル走査を分けること、新形式だけをパースすることについて、基本方針の変更は求めません。Low は、依頼文の取り扱いどおり、記録して v0.13.0 以降で対応できます。

### 問い 1〜7 への回答

1. **文字の集合の妥当性: 指摘なし。** 今回決めた対象に対し、双方向の 9 文字と U+2028・U+2029 の計 11 文字を検出する方針は妥当です。UTS #55 が禁止一辺倒の方針を採らないことを認識したうえで、字句解析を持たず表示環境も管理できない品質ゲートが、理由付きの allow と組み合わせて厳しく扱う説明は成立します。Rust の該当 lint も、同じ 9 文字を対象としています。ただし、11 文字がないことは、双方向表示による偽装全般がないことを意味しません。方向の印などの除外は、依頼された既知の限界として受け入れ、追加対象を要求しません。FORBIDDEN_RANGES を維持し、部分集合・件数・分類名の非衝突をテストする案も妥当です。資料: [UTS #55](https://www.unicode.org/reports/tr55/)、[Rust の deny-by-default lints](https://doc.rust-lang.org/rustc/lints/listing/deny-by-default.html)。

2. **分類を明示した allow だけが抑える設計: 方針に指摘なし。** 設計どおり、採用候補となる規則自身について、分類・パス・行・期限を確認すれば、分類なし規則や別分類規則による静かな抑制は防げます。パス名の finding を行指定規則から外すこと、秘密分類との名前の衝突を固定テストで防ぐこと、抑えた finding と使用回数を残すことも整合しています。ただし、その契約を複数規則の組合せで守るテストが不足しており、上記の Medium として扱いました。

3. **review-packet との二重化の回避: 指摘なし。** scanString は FileScanSink だけを使い、生の文字の検出を scanFile 側へ限定する構成なら、秘密の形として重複流入する経路を増やしません。共有する findAllowRule の変更も raw-char の kind に限定し、既存の秘密分類の照合を保つ限り、文書上は packet の秘密走査へ影響しません。T12 で scanString の結果を固定し、T13 で新しい allow 分類を受理した後にも packet が raw-char で exit 1 になることを確かめる組合せは妥当です。

4. **パーサ互換・履歴: 親子の版の説明に修正が必要です。** 新しい 6 内訳だけを受け付ける H8 と、パース結果が合否を変えない P1 は両立します。一方、旧 scanner を呼ぶ限り新しい検出能力は使えないため、食い違い全体を「表示だけ」とは説明できません。履歴については指摘なしです。rawChars がない古い run を 0 で補わず、unknownRuns・null とする案は、未測定と実測ゼロを混同しない扱いです。findings の系列は v0.13.0 から検出対象が広がるという設計上の前提で解釈する必要があります。

5. **テスト計画: 複数 allow 規則、内容を読まない対象のパス名、T5 の旧版期待値に指摘があります。** 長い行の窓の重複を T4、不正な UTF-8 の後ろにある有効な対象文字を T6、packet 経路の維持を T12・T13 で扱う方針には、それ以外の指摘はありません。T13 が旧版では新分類の設定エラーによる exit 2 となり、期待する exit 1 を満たさないという見込みは、設計の前提と整合します。その他の FAIL / PASS の見込みに、添付文書だけで断定できる追加の誤りは見つかりませんでした。既存テスト・fixture の変更一覧の完全性は、コード未添付のため未確認です。

6. **既知の限界: 保証範囲の限定には指摘なし。** UTF-16・不正な UTF-8・対象外文字・字句解析の欠如・ルートのパスなどを保証外として明記する方針を受け入れます。これらを今回の新規不具合として数えていません。ただし、「閉じた並び」を「害の無い並び」と言い換える文は不正確なので、Low の文書指摘としました。

7. **その他: U1〜U12 の推奨に、上記以外の反対すべき設計上の指摘はありません。** 部分集合の定数、U+ 表記の codePoint、行番号を持たないパス名 finding、対象文字の情報出力、ファイル・行・符号位置による重複除去、照合の共有関数への集約は整合しています。U7 の件数は、実際の文字の出現総数ではなく、この規則でまとめた finding 数として理解しました。テストを先に作って旧 commit で確認し、実装と一緒に commit する分け方も、各 commit の verify を通す方針と整合します。適用先の SHA 更新を実装レビュー完了後に行う H11 も維持できます。
