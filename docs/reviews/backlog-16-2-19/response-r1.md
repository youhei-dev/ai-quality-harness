## 実測

作業用ファイルは `tmp/backlog-16-2-19-r1/`（git 管理外）。実験は、記録した pgid にだけ `process.kill` を差し替え（最初の ESRCH を受けた後は、同じ番号の別の生きたグループが応答するふり。何も届けない）、実際の子プロセスを動かして数えた。

### M1: ESRCH を見た後の送信（v0.5.32・v0.5.33・修正の試作）

猶予 1.5 秒・確認 1 秒（既定の縮小）。E だけ既定値（5 秒・2 秒）。表は「最初の ESRCH の後に、その pgid へ送ったもの」。

| シナリオ | v0.5.32 | v0.5.33 | 修正 |
|---|---|---|---|
| A: `close` 未着、グループは SIGTERM の 0.7 秒後に消える | ESRCH を見ずに、消えたグループの番号へ SIGKILL（1.5 秒）。8.0 秒まで返らない | signal 0 が 71 回、SIGKILL が 1 回（1.5 秒）。2.5 秒で返る | 0 回・0 回。1.7 秒で返る |
| B: `close` が先、グループは 0.7 秒後に消える | 消えたグループの番号へ SIGKILL（1.5 秒） | SIGKILL なし（0.7 秒で返る） | 同じ |
| C: 最初のシグナルが ESRCH（leader が 0.2 秒で終わり、`close` は来ない。タイムアウト 0.9 秒） | SIGTERM が ESRCH、その後に SIGKILL | signal 0 が 99 回と SIGKILL | SIGTERM だけ |
| D: `terminateActiveChildren`（target 1 は SIGTERM で消え、target 2 は無視） | target 1 へ signal 0 が 53 回と SIGKILL | 同じ | target 1 へ 0 回。target 2 には SIGKILL が届く |
| E: 既定値、グループは 3.5 秒後に消える | 5.0 秒に SIGKILL。14.0 秒まで返らない | signal 0 が 137 回、5.0 秒に SIGKILL。7.0 秒で返り、「消えていない」と書く | 0 回・0 回。5.5 秒で返る |

- v0.5.32 は、5 つのすべてで、消えたグループの番号へ SIGKILL を送った（A・B・E は ESRCH を見ないまま、C・D は見た後に）。v0.5.33 は B で送らなくなり、A・E の待ちを有界にしたが、A・C・D・E で「消えたと分かっているのに送る」形が残った
- 実際の確率の見積り（推測）: pid は毎秒約 830 進み、1 周は約 2 分。消えたグループの番号が、SIGKILL までの数秒に再び割り当てられる確率は、1 回のケースの上限でおよそ 4%（そのチェックの起動から約 2 分以上たっていることと、「`close` が来ない」形が前提）

## 修正前の失敗

新しいテストを v0.5.33 の `src/` に当てると、7 件のうち **4 件が FAIL**（最初の ESRCH の後に何も送らない、待ちが消滅の最初の確認から数えられる、最初のシグナルが ESRCH のとき、`terminateActiveChildren`）、3 件（対照）が PASS（生きたグループは SIGKILL を受けて消える、`close` が先でグループが消えたら SIGKILL なし、Windows の分岐）。
Windows の対照は、win32 でも `gone` を立てる誤った修正（変異）で FAIL することを確かめた。

## 直さなかったもの・既知の限界

- **最初のシグナルの前**（項目 6）: leader が先に終わり、`close` が来ないまま（別のグループの孫が pipe を握る）タイムアウトまでの時間が長いと、最初の SIGTERM は確認なしで番号へ送られる。実測で同じ性質を確認した（v0.5.32・v0.5.33・この版）。人間の判断で、今回は直さず ROADMAP の候補にした
- 最後の確認から送信までの 25 ms の窓: `kill` が持つ競合で、消せない
- 安全弁をフェーズごとの期限にする案（Y2）、確認の起点を予定時刻にする案（Y1）: 採らなかった（ADR-0023 の代替案、ROADMAP の候補）
- Windows では v0.5.33 から、`close` 未着でも消滅の確認の起点が最初のポーリング（25 ms）になる（v0.5.32 は SIGKILL のタイマーまで待った）。Windows は対象外で、この版は変えない。ROADMAP の候補
- 実際の pgid の再利用は再現していない（差し替えで決定的に確かめた）。1.5 秒を超える停止との競合、レポートの書き込みが 1 秒を超える遅れ、Linux・Windows での実行は未確認

## 訂正（v0.5.36）

- 上の「レビュアーの主張と実測の食い違い」の補足 (1)（「実際の PGID 再利用を再現していない」は、`process.kill` の差し替えで決定的に再現した）は、**誤解を招く書き方だった**。差し替えで作ったのは「最初の ESRCH の後に、同じ番号が別の生きたグループとして応答する」状況で、**実際の PGID の再利用は再現していない**（レビュアーの指摘のとおり。この記録の末尾と ADR-0023 の既知の限界も、そう書いている）。差し替えで確かめたのは、その状況で runner が何を送るか（不変条件）である
- この訂正は、v0.5.35 の実装者の自レビュー S-5（`response-r2.md`）による。本文は記録として書き換えず、この節で訂正する
