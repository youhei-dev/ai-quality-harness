### 問い 2 (a). D3 の許容範囲と停止条件

版が変わった開発用項目の `version`・`resolved`・`integrity` と、その同じ版が宣言する `dependencies`・`peerDependencies` 等の依存範囲に限定する方針は、今回の更新実態に合っている。公開の固定コミットの lock で、vitest の6値、`@vitest/mocker` の1値、vite の2値という計9値の前後を確認した。追加・削除や版が変わらない項目の変更を許していない点は評価できる。

ただし、**差分の全列挙は人間による承認そのものではない**。今後の D3 の承認記録を明確にする必要がある（Low 指摘）。一方で、新しい版が `engines`・`license`・`os`・`cpu`・`bin`・`funding`・`optional` を変えた場合に停止するのは、正しい更新であっても人間が理由を確かめる保守的な条件であり、fail-closed の方針として妥当。すべての正しい更新を自動で通す必要はない。

### 問い 2 (b). lock の根の扱いの推奨

**推奨は「明記する」。この推奨自体は指摘件数に含めない。** `packages[""]` は版の変わった開発用パッケージそのものではないため、新しい D3 の「それ以外は停止」を文字どおり適用すると、`package.json` の承認済み範囲の写しまで停止対象と読める。現状も注記1で根の事実を説明しており、今回の lock 更新を不正とする必要はないが、将来の手順として例外の範囲を閉じておくほうが安全である。

追加する文案の趣旨: 「lock の根の `devDependencies` は、承認済みの `package.json` の変更を同一キー・同一値で反映した場合に限って許す。lock の最上位と根の `version` は、既存のリリース手順による npm の更新だけを許す。そのほかの根の欄の変更、対応しない範囲の変更、キーの追加・削除は停止して人が決める」。これはルートの変更を無条件に許すものではなく、D2 と v0.17.1 以降の版一致規則に合わせた限定的な例外である。

### 問い 3. 決定5・6の追加の確かめ

**決定5: 主要な抜けは補われた。** 非推奨を `npm view` で見ること、選定版を取得できるか確かめること、勧告を読むことは必要な追加である。「重大な安全上の警告」は、少なくとも npm audit の high・critical、公開済みの重大な安全上の非推奨理由、取り下げの警告を含むと明文化すると運用者による解釈の違いが減る。npm の勧告の読みで分かるのは npm audit が把握する範囲のみで、未公表の問題の不存在を保証しない。既存の `npm ci` は当時の lock と integrity に従ってインストールできた根拠だが、cache から入っていれば事後の外部取得可能性の証明ではない。この区別は Low 指摘のとおり。

**決定6: 件数だけの場合より改善している。** 勧告 ID・パッケージ・重大度の組を比較すれば、同じ件数で新規勧告と既存勧告の消滅が入れ替わっても新しい組を検出できる。重大度の変更も組の差になる。消滅した勧告は、件数の減少理由の記録と同じ考えで、消えた理由を分かる範囲で記録するとよい。同じ ID・パッケージ・重大度のまま影響の版の範囲だけが変わる場合はこの組の比較では見分けられない。重大度や実際に入る版への影響が変わる場合は、必要に応じて advisory の影響範囲も比較することを推奨する。
