## B4-D-Q1. `@types/node` を 24.19.2 に上げるか（設計 §2.5.3）

- **【確定】A**（人間の決定 2026-11-07）

- **A（推奨）. 上げない（`~24.13.3` のまま。lock は 24.13.6 のまま）。ほかの 3 つ（eslint・typescript-eslint・vite）は B4-Q5 のとおり上げる**
- B. B4-Q5 のとおり `~24.19.2` に上げる。新しい型の API を使わないことは、レビューと「実行の Node で全テスト」だけで守る
- C. 上げて、自己 CI の `node-version`（今は `ci.yml:38,67` の `"24.13.1"`）も 24.19 系に上げる

根拠:
- 自己 CI と手元の実行の Node は 24.13.1【実測: `ci.yml:38,67`、`node --version`】。`package.json` の `engines` は `>=24.0.0`
- 型が 24.19 になると、Node 24.14〜24.19 で足された API を使うコードが型検査を通る。そのコードは 24.13.1 の CI で、テストが通る道だけで落ちる（通らない道は気づかない）【推定】
- 試しでは、上げても型検査・lint・全テスト・verify は同じ結果（今のコードは新しい API を使っていない）【実測。設計 §2.5】。違いは「これから書くコード」を守る強さだけ
- 型を実行の Node に合わせる方が、fail closed の考え（通らないものを通さない）に近い。A でも、`engines` の下限（24.0）より新しい API はすでに型で許されている（24.13 の型）ので、守りは完全ではない（既知の限界として書く）
- C は自己 CI の版を変える別の決定（適用先の `node-version` は適用先が決める。ADR-0031）

止まるもの: v0.18.1 の依存の commit（`package.json` と lock の中身）

## B4-D-Q5. C-44: 両端に空白のある値の扱い（設計 §3.1.2）

- **【確定】A**（人間の決定 2026-11-07）

- **A（推奨）. `codeSpan()` をそのまま使う（バッククォートを含む値に加えて、空白で始まり空白で終わる〈空白だけではない〉値も、両端に空白を 1 つずつ足す形に変わる）**

## B4-D-Q8. 1c: `--id-prefix` が `-R<数>` で終わるとき（設計 §3.2）

- **【確定】A**（人間の決定 2026-11-07）

- **A（推奨）. 使い方の誤り（exit 2）にする。文は「`--id-prefix` は ID の `-R<回>` より前の部分（例: ID が `B3-D-R1-001` なら `B3-D`）」**
- B. 文だけ直す（ID の形の誤り `[id]` の文に手がかりを足す）
- C. A と B の両方

根拠:
- 【実測】指摘が 0 件のレビューでは、`--id-prefix TRIAL-R1` のような誤った接頭辞でも exit 0 で取り込まれ、`findings-r1.json` の `idPrefix` が誤ったまま残る（設計 §3.2.1）。B では 0 件のときに何も出ない。誤りは次の回の取り込み（前の回の接頭辞が違う、で exit 2）まで分からない
- 指摘があるときは、今も `[id] findings[0].id is not of the form B3-D-R2-R2-NNN` で止まる【実測】
- 今ある 19 の接頭辞に `-R<数>` で終わるものは無い【実測】。review-check と既存のファイルには影響しない
- 裏返し: `-R<数>` で終わる接頭辞（例 `M2-R1`）はこれから使えない。使い方の文と CONFIG ではなく README・手順書に書く

止まるもの: v0.18.2 の review-import の commit
