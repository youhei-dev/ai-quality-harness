# aiqh batch4-design R2 独立設計レビュー

対象: v0.18.1、v0.18.2、H11 の 5 回目の設計 R2。基準 commit: `3a6295a3ae2ce15d3a1329f50cb825529d9c72c5`。

## 全体の結論

件数: High 0 / Medium 0 / Low 0

High と Medium はともに 0。依頼書の終了条件を満たすので、この設計レビューは R2 で終了してよい。これは設計案に対する静的な判断であり、未実装のコードや今後の CI 結果を保証するものではない。新たな指摘は無い。

### R1 の 4 件の判定

- B4-D-R1-001: 解消。設計 §2.4.2 と ADR-0003 の追記の案 r2 の決定 1 は、`writeReports` が書いた `latest.md` と `latest.json` を読み戻した Buffer と、commit した期待値の Buffer を比較する。`history` と `latest.json` の一致も確かめる。書き込みで禁止文字が表記に変わることは `golden-probe-r2.md` の §結果と `base/src/report/write.ts` の `writeAtomic` の実装に整合する。fixture 自体に生の禁止文字を置かない。
- B4-D-R1-002: 解消。設計 §2.2 の手順 3 はローカルの `refs/tags/v*` とリモートの `git ls-remote --tags --refs` の ref 名を集合で比べ、送信する名前、注釈付きタグ、tag object、指す commit、リモートでの同名 ref の不在を個別に確かめる。これは元の `--no-contains` を使う手順より目的に合う。
- B4-D-R1-003: 解消。設計 §2.2 の手順 6 と §2.6 は、push の失敗や応答不明を未作成と断定せず、再送しないまま読み取り専用の `ls-remote` により三つの状態を分け、人間に判断を渡すようになった。
- B4-D-R1-004: 解消。設計 §2.4.3、§2.4.6 と ADR-0003 の追記の案 r2 の決定 5・6 は、期待値の内容だけでなく入力の check 数、状態、`parsed`、`command`、`cwd` の条件を独立に固定する。人の差分確認の記録と、同時変更によるすり抜けを技術的には完全に防げない限界の記述も妥当。

### 問い 1. 前回の指摘は直ったか

指摘なし。4 件とも上のとおり解消した。

golden の比較を `writeReports` の出力へ切り替えたことで、`renderMarkdown` の返り値ではなく実ファイルのバイト列を固定できる。`golden-probe-r2.md` は基準コードの試行で、`plain` の Markdown 1 行、`edge` の 4 行に書き込み前後の差があり、書いたファイルに対象の生の禁止文字は残らないと記録している。`latest.json` と `history` も同じだった。計画する `edge` の E1 から E8 を設計 §2.4.3 と突き合わせると、C-44 が変更する対象は Checks の表で E1、E2、E3、E4、E6、E7 の 6 行、失敗詳細で E3、E4、E5、E7 の 4 行、合計 10 行という計算で整合する。これは変更後の実測値ではなく、現行コードと入力からの予測である。

### 問い 2. 修正の裏返しによる新しい穴

指摘なし。golden が実際にファイルを書く設計になったことによる並行実行の衝突は、テストごとに別の一時ディレクトリを使用すれば避けられる。`base/src/report/write.ts` では `historyStamp` が固定の `startedAt` から同じ名前を作りうるが、異なる一時ディレクトリなら競合しない。同じディレクトリを再利用すると履歴名に連番が付くため、実装では一時ディレクトリの分離、`try/finally` 等での後始末、失敗時の残存ファイルを確認する。いずれも実装の確認事項であり、現行の設計案を差し戻す問題とは判断しない。

タグの比較は Git の ref 名を使うため、注釈付きタグの剥がした行を別タグと誤認しない。`refs/tags/v*` 以外のタグ名や大文字で始まる名前は列挙対象外だが、実際に送るのは単一の `refs/tags/vX.Y.Z` であり、追加タグを一緒に送る経路にはならない。同名の branch とも完全 ref で区別できる。送信前後のリモート状態が競合して変わっても、別の値なら送信が拒否されるか、事後照合で検知する設計である。`ls-remote` 自体の失敗も「確認不能」に分類し、再送しないので安全側に止まる。

入力条件の固定は意図した仕様変更時に期待値とテストを更新する負担を増やすが、src の変更と理由と人の確認を同じ変更単位で扱う運用で調整可能である。

### 問い 3. --no-contains の向きの訂正

指摘なし。前回の私の説明のうち「origin/main の祖先を指すタグは --no-contains の結果に通常出ない」は誤りだった。`--contains` は指定 commit がタグの先祖にある場合を選び、`--no-contains` はその否定になる。よって origin/main より古い release タグは、通常 `--no-contains origin/main` に入る。origin/main 自身を指すタグは入らない。設計 R2、`r1-response.md`、付録 A7 の実測による訂正は正しい。`git for-each-ref` の同種の指定も同じ包含関係で読む。`git ls-remote --refs` が注釈付きタグの剥がした疑似 ref を出さないことも、記載された実測とコマンドの用途に整合する。

### 問い 4. B4-Q2 の決め直し

指摘なし。`--id-prefix` の末尾に `-R` と数字が続く場合を exit 2 にする変更は、指摘 0 件の取り込みで接頭辞の誤指定が見過ごされるケースに有効。`/-R\d+$/` は `B3-D`、`M2-2-RI`、`B20`、先頭だけが `R1` の値を拒否しない一方、`TRIAL-R1` と `B3-D-R12` を拒否する。意図した接頭辞でもこの末尾形式を使うことはできなくなるが、制約を ADR-0026、README、`--help`、CHANGELOG に互換性の変更として記す方針は妥当。round 1 の空でない `previous` の拒否と、round 2 以降の正しい入力を通す条件も維持されている。

### 問い 5. 受け入れ基準、変異、未確認範囲

指摘なし。設計 §5 は、書かれたファイルの golden、履歴 JSON の一致、入力条件と期待値の検査、M13 から M15、タグの送信前後の確認、依存の再検証、C-44 と 1a・1c の変更前 FAIL と変更後 PASS、M1 から M12 と M16、H11 の設定再取得と適用先 A の人間の承認まで含む。§3.4 の M14 は書き込みの変換を飛ばすと golden が落ちること、M15 は入力の削減を検知すること、M16 は `[previous]` の問題種別を固定することを狙い、追加した設計に対応している。§8 は変更後の描画、GitHub ruleset 下のタグ作成、適用先の最新設定、Linux の依存検証などを未確認として明示している。

実装では `writeReports` の一時ディレクトリの独立性と清掃、履歴名を固定値と決め打ちせず返されたパスから読むこと、変異を実際に走らせて失敗を観測することを確認する。これらは受け入れ基準を具体化して実行する際の注意であり、追加指摘にはしない。
