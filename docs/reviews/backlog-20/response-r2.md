## 結果と問いへの答え（レビュアーの結論の要約。実装者の評価ではない）

- **B20-R1-001 は解消**: `refusedNodeOption()` が `process.execArgv` と `NODE_OPTIONS` の両方を調べ、対象の起動指定（warn・abort）を拒否する、とした
- **問い 1（拒否の規則は漏れなく効くか。安全な形を規則の範囲を超えて拒否していないか）**: `unhandled-rejections=warn` を `=` の形・空白区切りの形・複数指定の途中でも拒否し、`_` を `-` に正規化し、`abort-on-uncaught-exception` は肯定・否定・別の字句の中の出現でも拒否する。`NODE_OPTIONS` の引用符・`\`・通常の空白以外の区切り、知らないモード・値の欠けも拒否に倒す、とした。
  安全な `throw`・`strict`・`none`・`warn-with-error-code` は、そのまま読める形では拒否しない。引用符付きの安全なモード・上書き済みの warn・否定の形の abort などまで拒否するのは、依頼文と ADR-0024 決定 6 に明示された保守的な仕様で、欠陥として数えない、とした。Node のオプションの構文の全変種に対する実機の網羅は確かめていない、とした
- **問い 2（拒否の経路）**: コード上は要件を満たす、とした。拒否の理由はモジュールの初期化の時に決め、`parseAsync` より前に分岐する。`process.exitCode = EXIT_ERROR`、`tryWriteError()` 経由の定型の 1 行、`verify` のときの `VERIFY ERROR (Node option error)`。この分岐から check もレポートも呼ばれず、`NODE_OPTIONS` の生の文字列は出さない。テストが実際に成功したことは、パケットの verify の記録に依拠する、とした
- **問い 3（`--doc` で足したファイルを読んだうえで、v0.5.42 の未処理の例外の経路）**: 追加の High・Medium なし、とした。`onUnhandled()`（最初の事象だけを出口から通知、シグナルで中断済みならその終わり方を保つ、未中断なら exit 2・新しい check を止める・動いている子を片付ける・安全弁）、runner のプロセスグループの扱い、verify の判定の確定の前後のシグナルのハンドラの切り替えは、ADR-0023・0024 の意図と整合する、とした
- 3 つの問い以外にも、High・Medium に当たる問題は見つからなかった。依頼文の既知の限界（シグナルと例外の先着、安全弁がレポートより先に発火しうること）は再指摘していない
