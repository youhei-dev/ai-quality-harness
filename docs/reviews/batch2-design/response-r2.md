## 指摘ごとの対応

### B2-D-R2-001（Medium、設計）: LF で分けるだけでは、CRLF の CR を security の check と同じ扱いにできない

- 対応（設計〈最終〉§5.6 の「CR の扱い」、ADR-0039 の案〈最終〉の決定 1）: 54 の判断の前に、LF の直前の U+000D（1 つ）と文字列の終わりの U+000D（1 つ）を、`src/security/scan.ts` の `LineAssembler` と同じ条件で判断から外す。元の文字列と位置は保ち、出力の字面は変えない。行の途中の CR は今までどおり `control` の側
- テスト（設計〈最終〉§5.8 の N8 に足した）: CRLF、単独の CR、CR CR LF、終わりの CR、長い行と CRLF の分割で、パケット・出口・security の check の判断が一致すること
- 状態: `open`（`destination` v0.17.0。実装と確かめは v0.17.0 の実装レビュー）

### B2-D-R2-002（Medium、テスト）: 53-F の受け入れの条件が、17 の形すべての評価と時間の予算との両立を固定しきれていない

- 対応（設計〈最終〉§4.8 の「受け入れの条件」）: (1) 17 の形 × 5 つの道具の全部の組で測りが完走し、CPU の絶対の上限・比・作業量の時計の 3 つすべてを評価できたこと、(2) 打ち切りは検出の成功に数えず別に数える、(3) テストの時間が T3 の上限を超えるなら T3 の式で根拠つきで決め直す、(4) 二乗の変異は実際の P3 のテストを通して落ちた箇所を記録する
- 実装（`f0cf374`）: `tests/parse-output.test.ts` の P3
  - (1) 各形のテストは、5 つの道具それぞれで 64 KiB を 1 回、256 KiB と 1 MiB を 3 回ずつ読み、どの読みでも作業量の時計（`time-limit` にならない）を、64 KiB の 1 回と 3 回の最小に CPU の絶対の上限を、3 回の最小どうしに比を当て、最後に評価した道具の数が 5 であることを確かめる（`expect(evaluated).toBe(tools.length)`）。変更前のコードの全テストで 17 の形すべてが PASS（全部の組が完走し、3 つを評価した）
  - (2)(4) 変異: 設計 M14 の MUT-1・MUT-2 を写しの worktree の `src/parse/text.ts` に入れ、vitest で P3 のテストそのものを走らせた。今のテスト（壁時計）では、MUT-1 で 4 つの形・MUT-2 で 3 つの形が絶対の上限で落ちた。新しいテストでは、MUT-1 で 9 つ（絶対の上限 4・比 5）・MUT-2 で 8 つ（絶対の上限 3・比 5）が落ちた。比だけが見つけた 5 つの形は両方とも「summary lines again and again」「section headers」「pytest summary lines again and again」「pytest FAILED lines after the heading」「pytest headings without a summary」（1 MiB の CPU 時間は 582〜2,565 ms で、どれも絶対の上限の内）。作業量の時計の外れは 0。落ちた道具はどれも最初の道具 vitest（テストは最初の外れで止まる）。打ち切り（timeout）は 0、外側の見張りの打ち切りも 0
  - (3) 静かな全テスト 4 回（commit ① の最初の形〈上限の数だけが今と違う〉の SHA 固定の worktree の 1 回〈1 分平均 3.06 で開始〉と、作業ツリーの 3 回）の中で「only newlines」は 2,777〜5,501 ms で、T3 の式で 12 × 5.50 = 66.0 → 70 秒。上限を 40 秒から 70 秒にした（B2-Q15 の 1 の条件つきの `:277`）。T53-2（3.5 秒の CPU を使う）は同じ 4 回で 3,854〜5,544 ms で、上限は 12 × 5.54 = 66.5 → 70 秒

### B2-D-R2-003（Low、テスト）: text の照らしだけでは、AST だけを書き換えた汚染を見つけない

- 選んだ形: **残る制限として明記する**（負のテストも境界のテストも入れない）
  - 表（`REUSED`）は `tests/structure/typescript.ts` のモジュールの中だけの値で、export しない。helper の export の一覧（値 7・型 1）をテストで固定した（`tests/structure-typescript-reuse.test.ts` の「the table stays inside」）
  - AST だけの書き換え（`text` は同じ）は見つけない、を設計（最終）§1.6 と helper の説明に書いた（50 には ADR が無い〈設計 §1.9: テストの部品だけ〉ので、設計と helper の説明と ROADMAP の項目 50）
- 理由: (1) 負のテスト（AST を書き換えて、次の program が使わないことを確かめる）は、見つける仕組みを作らない限り FAIL する。見つける仕組みは、TypeScript 自身が束縛のときに共有の SourceFile のノードへ書き込むので、正当な書き込みと形で見分けられない。(2) 全ノードの写しや照らしを program ごとに行うと、約 600 の SourceFile を毎回たどり、使い回しの利益の大半を消す。(3) 呼び出しの境界のテスト（呼び手が書き換えられないこと）は、SourceFile を凍らせられないので作れない。(4) 呼び手は helper を使うテストとガードだけで、どれも読むだけ（中身を書き換えるのは汚染の確かめの T50-5 だけ）。AST を書き換えるテストを足すときは `reuse: false` を使う、と helper の説明に書いた
- 状態: `resolved`（`fixedIn` `7460e65`、`destination` v0.15.1。確かめは v0.15.1 の実装レビュー）
