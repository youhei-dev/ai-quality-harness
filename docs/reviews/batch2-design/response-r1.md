## 指摘ごとの対応

### B2-D-R1-001（Medium、設計）: 50-B の SourceFile のキャッシュの同一性と無効化の条件

- 指摘の要約: 絶対パスだけを鍵にすると、ファイルの更新や、解析の条件・compiler options・host の違いがあっても、古い SourceFile を使い回しうる。SourceFile は書き換えられるのに、その契約が無い。等価のテストが挙げた fixture に限られる
- 確かめたこと（R2）
  - TypeScript 5.9.3 の配布物（`node_modules/typescript/lib/typescript.js`）を読んだ。言語サービスは、SourceFile を program の間で共有する鍵に、`sourceFileAffectingCompilerOptions`（SourceFile か束縛に効く 11 の options）とモジュールの形（`impliedNodeFormat`）を使う（`getKeyForCompilationSettings`・`getDocumentRegistryBucketKeyWithMode`）。既定の host の `getSourceFile` は、読んだ中身と解析の条件だけで `createSourceFile` を呼ぶ（`createGetSourceFile`）
  - 鍵の試作（`tmp/batch2/r2/proto50/`）で、リポジトリの全ファイルの型の誤りの一覧が、5 つの program で表の有り無しで同じ。ほかに 4 つの場面を確かめた（編集の前後、違う解析の条件〈`jsx`・`target`〉、fixture と実ファイルの混在、汚染〈渡した SourceFile の `text` の書き換え〉）。2 つめ以降の作成は 77〜130 ms（中身の読み直しとハッシュを含む。ただし 1 回だけ 1,043 ms の揺れ）
- 対応（設計 §1.6）
  - 鍵: 正規化したパス・今 host の `readFile` で読んだ中身の SHA-256・解析の条件（`languageVersion`・`impliedNodeFormat`・`jsDocParsingMode`・`setParentNodes`）・上の 11 の options の値。ディスクの書き換えは、中身のハッシュで別の鍵になる
  - 使い回さないとき（fail closed）: `shouldCreateNewSourceFile` が真、解析の条件のオブジェクトに知らない欄がある、`languageVersion` が数でない、options の値が文字列にできない、`readFile` が投げた
  - fixture と、fixture で上書きしたファイルは、表に入れず、表から出さない
  - 汚染: 渡す前に、その SourceFile の `text` が今読んだ中身と同じかを確かめ、違えば捨てて作り直す（SourceFile は TypeScript が束縛の結果を書き込む共有のオブジェクトで、凍らせられない）
- 候補の漏れ: 50-B'（1 回のテストファイルの実行の間だけの不変の写し）を足して比べ、退けた（写しの後のディスクの変更に気づかない。50-B の読み直しの費用は小さい）
- テスト（設計 §1.8）: T50-1（同一の SourceFile。基準で FAIL）、T50-2〜T50-5（編集の前後・解析の条件・fixture の混在・汚染。守り）、T50-6（表の有り無しで型の誤りとガードの答えが同じ。builtin-r3 の全 fixture と 19 の編集、r4〜r6 の fixture、リポジトリそのまま。基準で FAIL〈呼び方が無い〉）、T50-7（使い回さない条件。基準で FAIL）
- 残り: TypeScript の文書の約束としての SourceFile の共有は確かめていない [要確認]。等価は、実装の段で T50-6 として全部の fixture で確かめる

### B2-D-R1-002（Medium、設計）: 54 の表示と JSON の保存、RGI を判断する範囲

- 指摘の要約: 表記の要件が、文字列としての表示と、JSON のデータの保存を区別していない。JSON の文字の並びを表記にすることと、読み戻した値を同じに保つことは別の条件。RGI を判断する範囲と、パケットが確かめる範囲の一致が決まっていない。review-import と通常のレポートの経路の違いも
- 確かめたこと（R2）
  - 出口の経路（コードを読んだ）: 表示の経路（端末の行と、端末の `--json`〈`safeJson`。値そのものを表記にしてから `JSON.stringify`〉）と、保存の経路（ファイルの JSON。レポートも review-import の findings も、`JSON.stringify` の後に `writeAtomic(…, "json")` の `escapeRawCharsAsJson` を通る。値は変えない）
  - 試作（`tmp/batch2/r2/proto54/`）
    - 値の上で決めた位置だけを `\uXXXX` で書く JSON の書き手で、12 の入力すべての読み戻しが同じ
    - 字面に、判断が表記にする文字は残らない。表記にする文字の無い入力では、字面が `JSON.stringify(value, null, 2)` と同じ
    - ランダムな 400 の文（2,654 の「行と符号位置」の組）で、出口の判断と `scanRawCharText` の finding が 0 件の食い違い
  - 素朴な広げ方の落とし穴 2 つ（同じ試作で確かめた）
    - 今の 4 桁の書き方を BMP の外に使うと、データが壊れる（`\ue0041` は U+E004 と `1` に読める）
    - `JSON.stringify` の後の字面の上で判断すると、値の上の判断とずれる。値 U+0007 U+FE0F U+20E3 は、値の上では U+FE0F が並びの外だが、字面の上では `\u0007` の `7` が keycap の並びを作り、除かれる
- 対応（設計 §5.6、ADR-0039 の案の決定 1・3・4）
  - 判断は元の文字列の上で、LF で分けた 1 行ずつを、行の終わりまで届いた 1 つの窓として。run は LF をまたがないので、複数行で変わらない。表記は元の位置で決めた後に 1 回の走査で当てる
  - 保存の経路: 値を変えない JSON の書き手（仮: `jsonForFile`）。`writeReports` と review-import の 2 か所で、今の `JSON.stringify` を替える。`writeAtomic` の `escapeRawCharsAsJson` は最後の門として残す
  - 表示の経路: 今の禁止の集合と同じく値を表記にする（端末の `--json` も）。この違いを ADR と利用者の文書に書く
- 候補の漏れ: 54-G（保存の経路は生のまま、表示の経路だけ表記）を足して比べ、退けた（追跡しているファイルの findings の JSON に生の文字が残り、次の verify まで気づかない。値を変えずに字面だけ表記にできる）
- テスト（設計 §5.8）
  - N4: `JSON.parse` の後の深い同一性を必須にし、入力にキー・配列・サロゲートの組と片方だけ・`\u` の字面・U+200D／U+FE0F の並びの中と外・旗のタグ文字・BMP の外・行の境目・keycap の部品を含める
  - N8: パケット・出口・security の check の判断の等しさ。複数行・連続した RGI の並び・行の端の並びを含める
  - N3: review-import の読み戻しの同一性
- 残り: 試作は 12 の入力と 400 の文だけ。実装の段で、性質のテスト（決まった種のランダムな入力）として入れる

### B2-D-R1-003（Medium、テスト）: 53 の検出力

- 指摘の要約: CPU 時間への変更は有力だが、二乗の変異が絶対の上限で必ず落ちるという主張は弱い（入力の長さ・CPU の速さに依る）。壁時計を捨てると、待つ時間を見る役はテスト全体の timeout に移る
- 確かめたこと（R2）
  - 比の上限を決めるための実測（`tmp/batch2/r2/proto53/ratio.ts`）: P3 の 17 の形 × 5 つの道具（85 の組）について、256 KiB と 1 MiB を 3 回ずつ読み、そのスレッドの CPU 時間を測った
    - 静かなとき: 比の最大 5.00（0.01 ms 台のごく短い読み）。20 ms 以上の組では 4.15〜4.28
    - 自分で終わる負荷のもと（1 分平均 34〜54）: 比の最大 6.44。20 ms 以上の組では 4.79〜5.55
    - `t(1 MiB) ≤ 8 × t(256 KiB) + 20 ms` は、両方の 85 の組すべてで満たした（3 回の最小どうしでも、1 回目どうしでも）
  - 二乗の変異 2 つ（`src/` を `tmp/` に写し、`prepareStream` の終わりに二乗の仕事を足した。どちらも作業量の時計の外）
    - MUT-1（行の数の二乗）: 17 の形のうち、比で落ちた 8、絶対の上限 3、60 秒の打ち切り 3、作業量の時計 0。比だけが見つけた形 5（1 MiB の CPU 時間 584〜2,467 ms。絶対の上限の内）
    - MUT-2（空でない行の数の二乗）: 比で落ちた 8、絶対の上限 3、60 秒の打ち切り 4、作業量の時計 0。比だけが見つけた形 4（913〜1,792 ms）
- 対応（設計 §4.6・§4.8）
  - 53-F: CPU 時間の絶対の上限（今の数）に、256 KiB と 1 MiB の比を足す（3 回の最小どうし）。8 は線形の 4 倍の 2 倍・二乗の 16 倍の半分、足す 20 ms はごく短い読みの揺れを外すため
  - 待つ時間（スレッドが止まる・CPU を待つ）は、テスト全体の上限（`it.each` の timeout）と suite の上限（T4）が受け持つと明記した
  - 受け入れの条件: 実装の段の報告に、わざと二乗にした変異で新しいテストが実際に落ちた記録を入れる
  - テストの時間は約 3.3 秒の見込み【推定】で、T3 の式で 40 秒のまま。実装の段で測り直し、超えれば上限を直す（B2-Q15 の条件つきの項）
- 候補の漏れ: 53-F（入力の長さの倍率で比べる）を推奨にした。53-G（決定的な操作の回数。製品の `src/parse/` に数える引数を足す）は、v0.15.1（src を変えない版）の範囲の外として残す
- テスト（設計 §4.8）: T53-1（待ちを数えない。基準で FAIL）、T53-2（CPU を使う遅さは数える。守り。待ちと CPU 消費を分けた）、T53-3（比の判定の関数。基準で FAIL）
- 残り: L2 と同じ強さ（1 分平均 200 以上）での比は測っていない。1 行の中の二乗（1 行は 4,096 単位まで）は入力の長さに対して線形なので比では見えず、絶対の上限が受け持つ

### B2-D-R1-004（Low、テスト）: 51 の Job Summary の失敗の道

- 指摘の要約: YAML の文の確かめと CI の画面の目視だけでは、書かれなかったときの 1 行・古いレポートを拾わないこと・違う `output.dir` が回帰テストで固定されない

- 対応（設計 §2.6・§2.8・§2.9）

  - 自己適用の job に `job-summary: true` を足す（B2-Q4 の A を「自己適用 ＋ 手元のテスト」に変えた）

### B2-D-R1-005（Low、文書）: 55 の守りのテスト

- 指摘の要約: 誤った選び方の維持を守りのテストにすると、将来の改善を不必要に縛る
- 対応（設計 §6.8・§6.9、付録 B の 6）
  - 守りのテストは、正しく件数が取れる wrapper の形（`cross-env`・`pnpm exec`・`npm exec`・`timeout`・`npm --prefix … audit`）が選ばれることだけにした
