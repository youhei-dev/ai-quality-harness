# aiqh batch2 設計 R1 独立レビュー

対象: ROADMAP 50〜55、基準 commit `8650a72355e8b606af0ee815044a525b5350e5bd`。本レビューは設計を対象とし、製品コードとテストは実行していない。実装者の実測値は再測定していない。

### B2-D-R1-001

- ID: B2-D-R1-001
- 重要度: Medium
- 種別: 設計
- 対象: 設計 §1.5〜§1.8、B2-Q1、tests/structure/typescript.ts
- 内容: SourceFile キャッシュの同一性条件と無効化条件が不足する。絶対パスだけを鍵にし、最初に構文解析したオブジェクトを以後共有すると、ファイルの更新、languageVersion・scriptKind・compiler options・ホストごとの違いがあっても古い SourceFile を再利用しうる。
- 根拠: 基準コードの createProgram は毎回 tsconfig を解析して新しい CompilerHost を作り、getSourceFile に languageVersion と shouldCreate を受ける。R1 は同一プロセスで options は同じと推定するが、既存の呼び口が複数の program を作れることと、SourceFile が可変であることを考慮した契約が無い。T50-3 の等しさは挙げた fixture に限定される。
- 修正案: 50-B の鍵を少なくとも正規化パス・有効なパース条件・ファイルの版で定義し、ディスクの書換えでは無効化する。あるいは1回のテスト実行中の明示的な不変スナップショットに限定し、例外を fail closed にする。テストで同一パスの編集前後・異なる構文条件・fixtures と実ファイルの混在・SourceFile 汚染・キャッシュ有無の結果同一を確認する。
- 確度: 確認済み

### B2-D-R1-002

- ID: B2-D-R1-002
- 重要度: Medium
- 種別: 設計
- 対象: 設計 §5.5〜§5.8、ADR-0039 決定 1・4、B2-Q9・B2-Q11
- 内容: 出口の表記の要件が、文字列としての表示と JSON データ保存を十分区別していない。JSON に見えない文字をエスケープした字面を出すことと、読み戻した値の同一性を保つことは別の条件である。また文字列の行ごとに RGI を解析する範囲と、パケットが検査する元の文字列の範囲の一致が未規定。
- 根拠: 基準の writeReports は JSON.stringify の後に writeAtomic へ渡し、output.ts は JSON の各キーと値も処理する。ADR 案は JSON を unicode escape にしてデータは同じと約束するが、JSON 構文化より前にバックスラッシュ列へ置き換える実装では読み戻し結果が変わる。review-import と通常レポートでも出力経路が異なる。
- 修正案: JSON は文字列値自体を変更せず、JSON.stringify 後の妥当なトークン内だけをエスケープするか、等価な JSON serializer を使う、と明記する。JSON.parse 後の深い同一性を必須テストにし、キー・配列・サロゲート・既存のエスケープ表記・U+200D／U+FE0F・行境界の入力を含める。パケット検査と出口の同一判断を、複数行と連続RGIのケースで固定する。
- 確度: 確認済み

### B2-D-R1-003

- ID: B2-D-R1-003
- 重要度: Medium
- 種別: テスト
- 対象: 設計 §4.6・§4.8、B2-Q7、tests/parse-output.test.ts
- 内容: CPU 時間への変更自体は有力だが、二乗の変異が既定の絶対上限で必ず落ちるという検出力の主張が弱い。CPU 時間が 3,000ms に届くかは入力の長さ・CPU性能に依存する。壁時計を捨てると、実際の長時間待機を検知する役割はテスト全体の timeout に移る。
- 根拠: 基準コード prepareStream は分割処理で文字列を走査し、P3 は長さの違う入力で作業量と壁時計を併用する。設計の T53-1 は待機を外すことのテストだが、変異テストの二乗化が CPU 閾値を越える証拠や相対的スケーリングの基準が定義されていない。
- 修正案: CPU 時間の絶対上限に加え、入力サイズ N と 2N／4N の CPU 時間の比、または決定的な操作回数カウンタによる増え方の検証を定義する。二乗の変異は実際にテストが落ちた記録を受け入れ条件とし、待機と CPU 消費を分けたテストを設ける。
- 確度: 確認済み

## 全体の結論

件数: High 0 / Medium 3 / Low 2

Medium が残るため、依頼文の設計レビュー終了基準に達しない。Q1 の50-B、Q7 の53-A、Q9 の54-Aは、上記の補強なしに推奨どおり確定することには反対する。その他の推奨には、確認範囲で重大な異議はない。

### 問い1: 各項目の問題の捉え方

50 の重複した program、51 の Job Summary のパス不一致、52 の startedAt が一意でないこと、53 の壁時計が負荷で変動すること、54 の入口と出口の層(c)の不一致、55 の既存パーサの偽陽性は、いずれも設計の中心問題として妥当。51 は GitHub Actions での実行ではなく手元で判定を再現した段階であり、その区別も妥当。54 は security の check が走査しない git メッセージやレビュー原文にも効くようにする動機を支持する。

### 問い2: 候補の漏れ

50 にはキャッシュを明示的な不変入力の寿命だけに限定する中間案、54 にはJSON保存経路と表示経路を分離する中間案を追加比較する価値がある。51 の専用出力先、52 の UUID、53 の CPU 時間はそれぞれ自然な候補だが、53 には入力長の倍率で時間増加を比較する方式も併記すべき。

### 問い3: 推奨の妥当さ

B2-Q1（50-A）は支持、50-B はSourceFileの寿命とキャッシュ無効化条件つきで支持。Q2 は現行基準のままでよい。Q3 は支持するが、Q4 は実行経路の失敗系をテストで守ることが望ましい。Q5・Q6 の UUID と端末を変えない案は支持する。新しい最上位キーを読み飛ばす旧読者の挙動は資料と実コードに整合するが、古いバージョン全般への保証ではない。Q7 は CPU 時間へ置換する方向を支持しつつ、検出力の追加条件が必要。Q8 は対象外のテストを今回は維持する判断に指摘なし。Q9 はJSONの読戻し同一性という契約を条件に支持、Q10 は allow を入口に適用しない判断を支持、Q11 は import を止めないことを支持するが JSON 表記の契約を固定すべき。Q12 は当面据置きを容認するが、偽陽性を望ましい仕様として固定しないこと。Q13〜Q16 はそのままの進行管理で概ね妥当。

### 問い4: テスト方針の検出力

50 のキャッシュあり／なしの等価性だけではファイル更新や構文条件の差に不足する。53 の変異は閾値を越えることを実行結果で確認する必要がある。54 は JSON.parse 後の同一性と、RGIの境界、文字列キー・異体字・複数行を必須にする。51 は手順の文字列検査だけでなく実行経路の失敗系が望ましい。52 のrunId不一致と同一ミリ秒のテストは妥当。B2-Q15 の既存の期待値の変更一覧は設計上明示されているが、全テストの grep や実行結果による網羅性は未検証。

### 問い5: 既存の出力・利用者への影響

51 は job-summary を有効にした利用者の report 出力先も変えるため、ログのパスだけでなく、同一job内の後続ステップが既定の場所を読む場合の影響を文書化したい。52 の schemaVersion 1 維持は追加キーを無視する現在の読み手には妥当だが、厳格な外部読者には変更となる。54 の JSON 文字列を表記にする変更は、データ内容を変えずにエンコードすることが条件。55 は表示専用であり、判定への影響を小さいと見ることに同意。

### 問い6: 版の分け方

V1（v0.15.1 → v0.16.0 → v0.17.0）は変更領域を分離でき、支持する。ただし v0.15.1 に入れる50-Bと53-Aは検出力の条件を確定してから実装すること。54-A を batch2 から外す積極的理由は現状ではないが、JSON同一性が設計で確定しない場合は v0.17.0 に進まずR2で補強すべき。
