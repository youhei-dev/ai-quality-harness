## 各指摘への対応

### B3-D-R1-001（Medium）
- **判定**: 正しい。R1 の設計は「8 行の組が 1 つなら読む」で、末尾 1 MiB の窓（`src/parse/text.ts` の `PARSE_INPUT_MAX`）や runner の 10 MiB（`src/runner/execute.ts:27`）で本物の要約が見えなくなり、テストが出した偽の 8 行だけが残る形を読んでしまう
- **調べたこと**: 切れたことは、今はパーサに伝わらない。runner は末尾を保持して `stdoutTruncated` を立て（`src/runner/execute.ts:277`）、`parseOutputAs` は窓の切れと合わせて `parsed.truncated` に書く（`src/parse/read.ts:67-72`）が、パーサには `{ stdout, stderr, exitCode }` だけを渡す（`src/parse/read.ts:75`、`src/parse/tool.ts:5-10`）
- **直し**（設計 R2 §3.3・§3.5・§3.11）:
  - パーサへの入力 `ParserInput` に `stdoutTruncated: boolean`（必須の欄）を足す。値は「runner が先頭を捨てた、または窓が先頭を切った」。ほかのパーサは読まない（振る舞いは変わらない）。パーサを呼ぶのは `src/parse/read.ts:75` の 1 か所だけで、テストはパーサを直接呼んでいない（`parseOutputAs` 経由）ので、テストの呼び出しの形は変わらない
  - node:test のパーサは、`stdoutTruncated` が真なら、組を数える前に `unparsed`・理由 `output-truncated` を返す（B3-D-Q13）。端末は `parsed: node-test — not read (output-truncated)`、`latest.md` の状態の欄は `unparsed (output-truncated)`
  - 理由の語を 1 つ足す（`ParseReason` と、パーサの答えの理由）。history の読み手は `parsed.reason` を読まない（`src/run-history/read.ts:156-161` の `PARSED` に `reason` が無く、知らないキーは捨てる）ので、新旧どちらの `aiqh history` にも影響しない。この理由が出るのは node:test の check だけで、そのレポートは `tool: "node-test"` のために v0.17.x の history では元から読めない（B3-D-Q6）
  - 切れていないときの組み立て: 出力の全体が見えるので、実行が要約まで進んでいれば本物の組が必ずある。テストが偽の組を出せば 2 組になり、`unexpected-summary`（R1 の B3-D-Q2 のまま）
  - **終了コードとの一致**（B3-D-Q14。R1 の指摘の外で足した確かめ）: 組が 1 つでも、終了コードが「fail + cancelled が 1 以上なら 1、そうでなければ 0」と合わなければ `unexpected-summary`。実行が要約の前に止められた（終了コードなし）形や、要約と食い違う形を読まない。取った 27 の形（R2 で、失敗した todo だけの形と、失敗のある npm 経由の形を足した）のすべてで、この関係が成り立った（設計 R2 §3.4）
  - 既知の限界（ADR-0028 の追記の案 R2）: 要約の出所は検証できない。実行が自分の要約の前に終わり（テストがプロセスを終わらせた、など）、テストが偽の組を 1 つだけ出し、その数が終了コードと合えば、その数を読む（判定・終了コードは変わらない）
- **テスト**: (a) 切れていない・本物だけ → parsed、(b) 切れていない・本物と偽 → `unexpected-summary`、(c) 切れた・偽だけが見える → `output-truncated`、(d) 切れた・本物だけが見える → `output-truncated`（決定どおり）。runner の切れ（`stdoutTruncated`）と窓の切れ（1 MiB を超える stdout）の両方で。試作で確かめた（設計 R2 §3.12）

### B3-D-R1-002（Low）
- **判定**: 正しい。R1 は「1〜15 桁の数」を組の成り立ちの条件に使い、同時に「16 桁以上は `unexpected-summary`」と書いていた（試作は `no-summary`）
- **直し**（設計 R2 §3.5・§3.12）: ① 字面の形: 8 行が同じ印（spec の `U+2139` と空白、または TAP の `# `）で、語がこの順、値が数字と点だけの 1 文字以上。② 値の確かめ: 7 つの数が 1〜15 桁の数字だけ、`duration_ms` が `<数字>` か `<数字>.<数字>`、和、終了コード。① の組が 0 なら `no-summary`、2 以上なら `unexpected-summary`、1 で ② を通らなければ `unexpected-summary`
- **テスト**: 境目の表（設計 R2 §3.12 の e01〜e21）。正常 8 行、数の 1 行だけ 16 桁（ほかの 7 行は正しい）、16 桁の組と正常な組の共存、15 桁ちょうど、語が 1 つ違う、行の順が違う、印が混ざる、値の形はあるが意味が無い（`1.2.3`・`1.5`）、和が合わない、終了コードが合わない・無い、字下げ、7 行、空の値、先頭の 0、切れて組なし、前に余分な行、spec と TAP の 2 組、窓の始まりで組が切れる

### B3-D-R1-003（Low）
- **判定**: 正しい。R1 の推奨（A: 0.5.35 に戻す）は、npm の出力を手で書き換える運用を、理由を確かめないまま固定していた
- **理由の調べ**（設計 R2 §2.6）: ルートの version は、M0 で 0.1.0、`484703f`（v0.5.35 のころの依存の更新）で npm が 0.5.35 に揃え、そのまま受け入れた。v0.13.2（`4163ad2`）と v0.14.1（`b62519c`）は、npm が書いた値を手で 0.5.35 に戻した。commit のメッセージは「the old mismatch with package.json is not fixed here」と「as in v0.13.2」。リポジトリの記録（CHANGELOG・ROADMAP・ADR・`docs/reviews/`・プロジェクトの CLAUDE.md）に、0.5.35 であることの意味や守る理由は**無い**（各版の CHANGELOG の「0.5.35 のまま」は事実の記録）。v0.13.2 の作業の指示（公開リポジトリの外）の趣旨は「前からの食い違いは、この版では直さない」で、その版の範囲を承認した依存の変更に絞るためだった
- **0.5.35 に頼るもの**: 無い。`git grep '0\.5\.35'` の当たりは、過去の版の記録の文だけ。lock を読むコード・テストは、lock があるか（init の依存の監査の提案）と、パケットでの種類（`lock`）だけ
