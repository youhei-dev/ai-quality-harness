# batch3-design R2 独立設計レビュー

対象: v0.17.1・v0.18.0 の設計案 R2。基準 commit `447fb663297096aee42535cad253ad280a22a00f`。実装前の設計についての静的な独立レビューであり、試作・テストを独立実行したものではない。

### B3-D-R2-001

- **ID**: B3-D-R2-001
- **重要度**: Medium
- **種別**: 設計
- **対象**: 設計 §3.3・§3.5・§3.11・§3.12、ADR-0028 追記案 R2 決定 14、B3-D-Q13
- **内容**: stdout の先頭が 1 MiB の解析窓から落ちただけで、末尾に完全な正規の node:test 要約が残っていても、件数を常に output-truncated として捨てる。大量のテストや通常の console.log が多い正常な実行ほど表示機能を失う。誤表示を避ける安全側の設計としては正しいが、node:test パーサ導入の実用上の受け入れ条件が欠けている。
- **根拠**: batch3-design-r2.md §3.3 の PARSE_INPUT_MAX 1 MiB と §3.5 規則 0、§3.11 の stdoutTruncated 合成、§3.12 d1・d2 は、完全な正規要約だけが末尾にあっても一律 unparsed とする。base/src/parse/read.ts:67-75 は従来パーサに切断情報を渡さず、base/src/parse/text.ts の prepareStream が末尾を保つ。これは R1 の偽件数問題を防ぐ一方で、大規模実行の観測可能性を恒常的に下げる。頻度は適用先 A の実物を未収集なので未確定。
- **修正案**: 現行の fail closed な規則を暫定維持し、実装前に適用先 A と大規模の合成入力で stdout 総量・要約の検出率を測る受け入れ条件を足す。通常の spec で 1 MiB を越えるケースに備え、(a) 要約の真正性を独立に保証できる専用の reporter 出力を別チャネル・別ファイルへ記録し検証する案、(b) 先頭と末尾の両方を保持し、どちらにも候補がないと判定できる追加の監視状態を持つ案を比較する。単純に末尾窓を大きくする、最後の 8 行だけを無条件で信じる、末尾に正規らしい組があるだけで切断を無視する案は偽件数を再導入するので採用しない。安全な追加策がこの版に入らない場合でも、どのサイズ・条件で件数が出なくなるかを受け入れ基準・文書・回帰テストで固定し、改善の ROADMAP を明示する。
- **確度**: 確認済み

## 全体の結論

件数: High 0 / Medium 1 / Low 0

**High・Medium が 0 の終了基準には未達**。R1 の危険な偽件数を防ぐ直しは成立している。一方で正常な大規模テストの件数を恒常的に捨てる設計を、実態の計測と改善の判断なしで既知の限界として閉じるのは不十分。既定の fail closed を弱めることは勧めない。

### R1 の3件の再判定

- B3-D-R1-001: 解消。stdout の切断を runner と解析窓の両方から ParserInput に伝え、切れている場合は件数を読まず output-truncated とするため、元の偽の 8 行だけを parsed にする経路は防いだ。ただし正常な大容量出力でも件数を失う新しい実用上の問題は別途指摘。
- B3-D-R1-002: 解消。8 行の字面による組の数え上げと値の検査を分離し、16 桁の数・小数・空・混在・2 組を §3.12 の表で一意に分類した。
- B3-D-R1-003: 解消。0.5.35 を維持する根拠を調べ、npm ci・install・pack 等の試作を比較し、npm の版と揃える B 案へ改め、リリース手順と守りのテストまで定義した。

### 問い 1: R1 の3件の対応

上の再判定のとおり。stdout の切断をパーサに正しく伝え、出所の不確かな要約を出さない対応は R1-001 の元の不備を解消する。偽の組が本物の組と共存する場合の unexpected-summary、組の形と値を分ける境界も R2 で明確になった。lock の版合わせは古い値を手で維持するより再現性がある。

### 問い 2: R2 の変更で新たに生じた問題

node:test の output-truncated は stdout の切断だけを条件とし、stderr の切断は条件にしないため、要約を stdout で読むという前提とは整合する。`ParserInput` に必須の boolean を足し、`src/parse/read.ts` で runner と 1 MiB の窓の切断の論理和を渡す設計は筋が通る。`ParseReason`・`ParserAnswer`・読取り側の通過条件の追加が必要であり、§3.11 とテスト計画にある。history は reason を保持しない設計なので、新しい理由の語自体は旧来の読み手の互換を追加で破らない。一方、`node-test` という新しい tool は古い読み手で bad-shape になり得ると文書化されており、別問題である。

終了コードと fail・cancelled の数の照合は、実測した Node v24.13.1 の 27 形では成立している。ただし Node の全バージョンや wrapper の全形への一般化は確認されていないため、実装時に適用先 A の実出力で確かめる条件を支持する。正しい要約を拒む向きであって verify の合否は変えない。

**追加の検討（ユーザー指定）**: 完全な spec 要約が stdout の末尾に残っていても、1 MiB 超では必ず unparsed となる。誤った件数を表示するより件数を表示しない方が fail closed に沿うので、一律切断拒否の安全性は支持する。ただし多数のテストや大量の console.log は異常でない。利用者の期待する件数表示が失われる頻度を測定せず、単なる既知の限界として完了扱いすることには反対する。末尾だけを信じる変更は安全でないため、独立の reporter チャネルの設計を優先比較し、導入を見送るなら具体的な運用指標と追跡項目を残すべき。

### 問い 3: lock の結論と手順

B 案を支持。設計 §2.6 と `lock-measurements-r2.md` では、npm ci・導入された依存・pack の結果に有意な違いを認めず、古い版を保持する案だけが npm install で二行を書き直される。`npm version 0.17.1 --no-git-tag-version` をリリース時に使い、`package.json` と lock のルート二箇所を照合するのは妥当。依存更新 commit では現行の package.json と同じ旧バージョンを保ち、リリース commit でまとめて新バージョンに進める順序にも矛盾は見当たらない。npm のスクリプト・lock の他の欄の変化を実装時に機械的に検査する条件は維持すること。追加の指摘なし。

### 問い 4: その他の見落とし

項目40の線形走査は、BEGIN の行の印・最初の END・途中の END 不在・次の一致の開始位置について、正規表現を正解とした同値テストと CPU 時間の倍率で確認する計画がある。正規表現の元の伏せる範囲を縮めないことが受入基準であり、設計から新しい High・Medium の不備は確認しなかった。Actions の SHA 更新は、タグの peeled commit を採り、人間の承認と互換を確認する手順として読める。適用先への反映と ruleset 設定を版の外に分ける判断も支持する。追加の指摘なし。
