## B3-D-R2-001 への対応

- **判定**: 正しい。R2 の規則は偽の件数を防ぐが、正常な大きな実行で件数が出なくなる条件と頻度を測らずに、既知の限界として閉じていた
- **実測**（設計（最終）§3.13、付録 A9）
  - 適用先 A の実物（追跡外の場所の写し〈`git clone --no-hardlinks`〉で `npm ci` の後、`NO_COLOR=1`・非 TTY・外への通信を止めて unit の check のコマンドを 1 回）: stdout 12,422 バイト・125 行・UTF-16 で 5,914 単位（読む窓の約 0.6%）、stderr 0 バイト、113 件、exit 0。要約の 8 行は設計の段の形と同じで、和と終了コードも合った。R2 の試作のパーサは `tests 113 (pass 113, fail 0); suites 0` と読んだ
  - 合成の入力（名前 46 文字ほどのテストを 1,000〜50,000 件、1 テストあたりの `console.log` 0・1・10 行。15 通り）: 1 テストあたり、spec の出力は UTF-16 で 60.7 単位（`console.log` 1 行で 107.7、10 行で 530.7）。読む窓（1,048,576 単位）を超えるのは、`console.log` 無しで約 17,000 件、1 行で約 9,700 件、10 行で約 2,000 件。runner の保持（10 MiB）を超えるのは、それぞれ約 167,000・96,000・20,000 件で、窓が先に当たる
  - 境目ちょうど: stdout が 1,048,576 単位ちょうど（最後に正しい要約）なら `parsed`、1 単位多ければ `output-truncated`。runner の切れの印だけでも `output-truncated`
- **固定**
  - ADR-0028 の追記の案（最終）の決定 14 に「件数が出なくなる条件」（窓の長さで、件数の目安と適用先 A の実物の値）を書いた
  - v0.18.0 の回帰テスト: 境目ちょうど（parsed）と 1 単位上（output-truncated）、runner の切れの印、合成の大きな出力（窓を超える形）
  - 受け入れの基準（設計（最終）§5.3）: 上のテストが通ること、適用先 A の実物の出力を実装の段で写しの中でもう一度取り、件数が正しく出ること、H11 の 4 回目で適用先 A の CI に `parsed: node-test` の行が出ること
- **改善策**（ROADMAP の項目 56、行き先は見張り）: runner が stdout を流しながら（保持する末尾とは別に）、要約の形の組を全体で数える状態を持ち、全体で 1 組で、その組が末尾の窓にあれば読む
  - (a) 専用の reporter を別ファイルに出させる案は候補にしない: 利用者の check のコマンドに reporter と出力先のオプションを足すことになり、aiqh は check のコマンドを変えない（ADR-0028 の P5、ADR-0005 の「設定 → 子プロセス → 終了コード」の 1 本の経路）。reporter の出力は利用者の端末・ログの見え方も変える
  - 末尾の窓を大きくするだけの案: 窓の外に落ちた組を見つけられない形が残る（偽の組が窓に残る形は大きさを変えても作れる）
  - 最後の組を無条件に信じる案: R1 の偽の件数を戻す
  - 選び直すきっかけ: 適用先・利用者の node:test の check で `output-truncated` が出たとき
