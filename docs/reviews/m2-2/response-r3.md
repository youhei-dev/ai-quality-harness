| (c) 対照: LF を含む `--cwd` の review-packet（`"escape"` モード） | exit 0。パスの LF は `\u{A}` の表記になり、出力は 3 行のまま |

### M2-2-R3-002（Medium）— (a) は再現できた。(b) 利用者由来のキーは無かった。High の基準には当たらない

- (a) `safeJson({ "key<U+202E>x": "value<U+202E>y" })`: 出力に生の U+202E が 1 個（キーの側）。値の側は `\u{202E}` の表記になる
- (b) 各コマンドの `--json` に利用者由来の値を多く入れて実行し、出力の JSON のオブジェクトのキーを全件集めた（コードでも、出力の型のキーが型で決まっていることを確かめた）

| コマンド | 入れた利用者由来の値 | キーの数（種類） | 利用者由来のキー | 出力の生の禁止文字 |
|---|---|---|---|---|
| security-scan `--json` | フォルダ名・ファイル名に U+202E、秘密の形の finding、allow の規則（使用・未使用）、`.env` の例のファイル | 46（25） | 無し | 0 |
| init `--json` | package.json の `name`・`scripts` と `dependencies` のキーに U+202E | 98（32） | 無し | 0 |
| review-packet `--json` | フォルダ名・変更ファイル名・依頼文の名前に U+202E（finding あり） | 32（20） | 無し | 0 |
| verify | `--json` は無い | — | — | — |

- キーはすべて固定の ASCII の識別子（`findings`・`file`・`root` など）だった。init は package.json の `scripts` のキーを JSON のキーにしない（不足する script 名の配列だけを出す）
- 参考: verify のファイルのレポート `latest.json`（端末への出力ではない）もキーは固定（42 種類）。project 名の U+202E は値として生で残る（既知のバックログ「ファイルへの出力の禁止文字」）。設定の check 名はスキーマで `^[a-z0-9][a-z0-9-]*$` に制限されている
- 利用者由来のキーは 1 つも無く、実測で生の禁止文字は出なかったので、High の基準（(b) で利用者由来のキーが見つかり、生の禁止文字が出る）には当たらない。`safeJson()` を共通の関数として使う将来の呼び出しへの保証の不足として Medium のまま

### M2-2-R3-003（Medium）— 再現できた。High の基準には当たらない

- (a) fixture `const key: "stdout" = "stdout"; process[key].write("x")`（型検査は通る）: `outputReferences()` は 0 件（検出しない）。対照の `process["stderr"].write("x")` は 1 件検出する
- (b) `src/output.ts` の写し（仮想ファイル）に `console.error(raw)` を足した: `src/output.ts` の中の参照としては 6 件（足した行を含む）見えるが、構造テストが見る `src/` の違反は 0 件（ファイル単位で許可しているため）
- 今の `src/` に、動的な `process[…]`・`console[…]`・`globalThis[…]` は無い（grep）。構造テストの穴で、今の出力が漏れているわけではない

## 対応

- 3 件とも **バックログへ（v0.5.3 では修正しない）**。ROADMAP のバックログに次の位置で足した（既存の順序は変えず、番号だけ振り直した）
  - 先頭: 1. M2-2-R3-002（`safeJson()` のキーを表記にする。表記の後にキーが衝突したら fail closed）、2. M2-2-R3-001（利用者由来の値を埋め込む前に LF・TAB も表記にする。`safeField()` と `safeBlock()` を分ける）
  - 構造ガードの項目（M2-2-R1-003）の直後: M2-2-R3-003（動的な `process[key]` の検出と、`src/output.ts` の中の書き出し場所の限定）
  - 「ファイルへの出力の禁止文字」の直後: verify の check に `NO_COLOR` を渡す（v0.5.2 の SP2 報告 §12-3 の人間の判断）
- 保証の記述の訂正: ADR-0016 に既知の限界 3 点を明記し、ARCHITECTURE の「端末への出力の出口」にも短く書いた

## 教訓

- **「残す」と決めた文字（LF・TAB）も、利用者由来の値の中では見た目を崩せる**: コマンド自身の書式としての改行と、埋め込む値の中の改行を区別する必要がある
- **共通の関数の保証は、受け取りうるすべての形で確かめる**: 値は表記にしていたが、オブジェクトのキーは確かめていなかった
- **構造ガードの許可をファイル単位にすると、許可したファイルの中の変化は見えない**: 許可する書き出しの場所（関数）まで限定する
