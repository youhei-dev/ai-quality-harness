## B5-D-Q1. v0.18.3 の記録の commit を、まとめるか分けるか（設計 §2.4）

- **【確定】A**（人間の決定 2026-11-08）


- **A（推奨）. 記録を 2 つに分ける: 「記録」（ADR-0001・0008・0028 の注記と追記、ci 手順書 §3・§5・§8、ROADMAP）と「設計の記録」（`docs/reviews/batch5-design/`。設計 R1 の取り込みの findings を含む）。版の commit は 依存 → 記録 → 設計の記録 → release の 4 つ**
- B. docs の commit を 1 つにする（依存 → docs → release の 3 つ。v0.18.1 の形）
- C. 記録を項目ごとに分ける（ADR ごと・手順書・ROADMAP で 5〜6 commit）

根拠:
- 設計の記録の commit には `aiqh review-import` が書いた `findings-r1.json` が入る。review-import は `--cwd` を基準に書くので、取り込みの結果を確かめてから別の commit にすると、差分とレビューのパケットで、手で書いた記録とコマンドが書いた記録を分けて読める
- 記録（ADR・手順書・ROADMAP）は、どれも「範囲の洗い出しの事実と B5-Q の決定を写す」1 つの目的で、互いに参照し合う（ADR-0028 の注記と ci 手順書と ROADMAP が同じ事実を指す）。分けると、途中の commit で参照が片方だけになる
- 各 commit は SHA 固定の worktree で typecheck・lint・全テスト・`npm run verify` を通す決まり（1 commit で 5 分前後）。C は検証の回数だけが増え、目的は分かれない

退けた理由: B は、手の記録とコマンドの記録が 1 つの差分に混ざる（batch4 の v0.18.1 は設計の記録と docs を 1 commit にしたが、取り込みの findings は無かった）。C は上のとおり

止まるもの: v0.18.3 の記録の commit

## B5-D-Q2. ci 手順書に gh CLI の版をどこまで書くか（設計 §2.2 の 4）

- **【確定】A**（人間の決定 2026-11-08）
- **R1 の条件**（B5-D-R1-002 の反映）: telemetry は、設定（`gh config get telemetry` が `disabled`）と、環境変数 `GH_TELEMETRY` の実効値の**両方**で確かめる。順は、gh のどのコマンドよりも先に `printenv GH_TELEMETRY`（`false`・`0`・`disabled` のどれかでなければ、gh を走らせずに止まる）→ 設定 → 版（設計 §2.1.3 の 1、`ci-doc-section3-draft-final.md` の (3)）


- **A（推奨）. 確かめた版（2.103.3）と、手順の前提にする最低の版（2.99.0 以上）を書き、telemetry を止めていることを条件にする。§8 の手順 8（次の版の着手前の確認）に `gh --version` と `gh config get telemetry` の確かめを足す**

退けた理由: B は上のとおり。C は、2.89.0 のような古い版のまま手順を走らせることを止められない

止まるもの: v0.18.3 の記録の commit（ci 手順書）

## B5-D-Q6. v0.18.4 の commit の分け方（設計 §3.6）

- **【確定】A**（人間の決定 2026-11-08）


- **A（推奨）. C-44 の commit（`src/report/markdown.ts` の 1 行と、その直前の注釈 2 行、golden の 2 つの `latest.md`、テストの直しと足し）→ 文書（ADR-0028 の注記、ROADMAP。設計の記録の追記があれば）→ release（版、CHANGELOG、README の状態の行）の 3 つ。テストを先に書いたことは、直す前の commit（v0.18.3 の release の commit）の SHA 固定の worktree に、新しいテストのファイルを写して走らせた FAIL の記録で示す（v0.18.2 と同じ）**
- B. テストの commit を先に分ける（テスト → 直し → 文書 → release の 4 つ）
- C. A の C-44 の commit を、src とテスト（golden を除く）と、golden の 2 つに分ける

根拠:
- プロジェクトの決まりで、各 commit は SHA 固定の worktree で全テストと `npm run verify` を通し、1 件でも FAIL なら push しない。B のテストの commit は、直す前の src と期待値に対して FAIL する（設計の段の試しで、直した後の 2 つのテストのファイルを基準の commit の src と期待値に当てると、56 件中 12 件 FAIL: 足す 6 件と直す既存の 6 件）。テストを `it.fails` や skip にして通すのは、テストを弱めることになる
- ADR-0003 の追記の決定 5: golden の期待値を変えてよいのは、出力を変える src の変更と同じ commit の中だけ（C はこれに反する）
- v0.18.2 も、テストを先に書いて直す前の SHA で FAIL を記録し（C-44: 42 件中 33 件 FAIL）、テストと直しを同じ commit に入れた（CHANGELOG の v0.18.2）

退けた理由: B は上のとおり、テストの commit が verify を通らない（決まりの例外を人間が決める必要がある）。C は ADR-0003 の決定 5 に反する

## B5-D-Q7. v0.18.3 の依存の試しで、決めた完了条件の 1 つが外れたときの扱い（設計 §2.1.3）

- **【確定】A**（人間の決定 2026-11-08）
- **R1 の条件**（B5-D-R1-001 の反映）: 版の不一致（lock・`npm ls`・`package.json` の範囲のどれかが、vitest 5.1.0・vite 8.3.6・`~5.1.0`・`~8.3.5` と違う。更新されていない場合を含む）と、着手時に registry で新しい版が出ていたことも、停止の条件に含める（設計 §2.1.3 の 2・5 の D13・6）


- **A（推奨）. 規則・テストを緩めず、依存の commit を外して止め、人間が決める（vitest だけ外す・vite だけ入れる・見送る）。記録だけの v0.18.3 は、依存なしでも出せる形にしておく（記録の commit は依存の commit に依らない）**

- C. 外れた原因を直して続ける（例: lint の新しい指摘をコードで直す）

根拠:
- 依存の更新は、承認された一覧の範囲だけで行う決まり（プロジェクトの規則）。一部を外すのも、承認の内容を変えることになる

退けた理由: B は承認の範囲を実装者が変える。C は、src を変えないと決めた版で src を変えうる（lint の指摘をテストのコードで直すだけなら範囲の中だが、どこまでが範囲かを実装者が決めることになる）

止まるもの: v0.18.3 の依存の commit（外れたときだけ）
