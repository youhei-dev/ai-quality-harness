# ADR-0023: 確認できなかった終了を、終了したことにしない

- 状態: 採用（ADR-0005 の「猶予後も生存していれば SIGKILL」の後に、消滅の確認と有界時間を足す。ADR-0005 は変えない。ARCHITECTURE §8 の「タイムアウト後の後始末ライフサイクル」の確定の条件を置き換える。v0.5.34 で、独立レビュー R1 を受けて、消えたと分かった group へ以後何も送らない決定 9 を足し、決定 7〈安全弁との関係〉の表現を狭めた。v0.5.35 で、独立レビュー R2 を受けて、決定 9 に「グループ経路があるときは、消えたと分かった group の leader へも送らない」を足し、v0.5.34 の範囲節の `close` 未着の待ちの起点の記述を訂正した〈実装の動きは、B16-R2-001 の 1 点だけ〉。v0.5.36 で、独立レビュー R3・実装者の自レビュー・実装者が信号の経路の一覧の作成中に見つけた経路を受けて、決定 6 の errno の保持、`terminateActiveChildren` の全対象の確認、決定 9 に「直接送信が ESRCH を返した leader の pid へは、以後直接送らない」を足した）
- 日付: 2026-10-05（M2-2、v0.5.33。ROADMAP のバックログ 16・2）。追記: 2026-10-05（v0.5.34。独立レビュー R1 の B16-R1-001・B16-R1-002）、2026-10-06（v0.5.35。独立レビュー R2 の B16-R2-001・B16-R2-002）、2026-10-10（v0.5.36。独立レビュー R3 の B16-R3-001、自レビュー S-1〜S-6、leader の pid）、2026-10-10（独立レビュー R4〈指摘なし〉の後。「範囲（v0.5.36 で追記）」の leader の pid の項に訂正の注記だけ）

## 文脈
- 原則は ADR-0022 と同じ向き: **確認できなかったものを、確認できたことにしない**。子プロセスを止めるときは、「シグナルを送った」ことと「グループが消えた」ことは別の事実
- v0.5.32 のコード（`src/runner/execute.ts`）は、タイムアウトまたは中断の後、SIGTERM → 猶予 → SIGKILL と送り、SIGKILL を送った後は `close` が来れば**グループの消滅を確かめずに確定**した。
  `close` が来なければ、タイムアウトの経路には上限が無かった。レポートの文言は、確認の有無にかかわらず常に `(process group terminated)` だった
- 実測（v0.5.32、SP1。`executeCommand` と実 CLI。macOS）:
  - **16**: (1) SIGKILL の経路は、返った時点でグループがまだ残っていた（5 回中 5 回。消えたのは 3〜6 ms 後）。(2) SIGTERM の直後に `close` が来て、グループが 0.4 秒後に消えるとき、猶予の終わりまで待った
    （猶予 3 秒で 4.5 秒。消滅は約 1.9 秒）。(3) 別のプロセスグループ（`detached`）の孫が stdout / stderr の pipe を握ると、**SIGKILL はその孫に届かず、孫が終わるまで返らなかった**
    （タイムアウトの経路。孫の寿命 20 秒で、CLI は 20.3 秒後に返った。中断の経路は CLI の安全弁〈猶予 + 3 秒 = 8 秒〉で終わるが、レポートを書かずに終了した）。(4) 文言 `(process group terminated)` は、(1)〜(3) でも出た
  - **2**: グループへの kill も子への kill も EPERM のとき（同じプロセスの中で模擬。本物の EPERM は再現していない）、`child.kill()` が出す `error` イベントを `spawn failed: kill EPERM` として扱い、**1.0 秒で確定した。
    子は動き続けていた**。`error` は `killTree` の中で同期的に出るため、確定の時点では SIGKILL のタイマーがまだ無く、確定の後も残って kill を試み続けた。タイムアウトの文言は `failed to start: spawn failed: kill EPERM`（起動していないかのような文言）
- fail closed は元から保たれていた（タイムアウトは FAIL、中断は SKIPPED・verdict ERROR で、終了コードは 1 / 130 / 143）。問題は、**確認していないことを確認したように書くこと**と、**待ちに上限が無いこと**

## 決定
1. **確定の条件**（タイムアウトまたは中断の後）: `close` が来て、かつ `kill(-pgid, 0)` が ESRCH（グループ消滅）を返したとき。25 ms ごとに確認する。`close` の後にグループが残っていれば、猶予の終わりを待たず、消えた時点で確定する
2. **有界時間**: SIGKILL を送った後（SIGKILL の前にグループが消えたのに `close` が来ないときは、消えたと分かった時点から）、最大 `confirmMs`（既定 2,000 ms、`DEFAULT_CONFIRM_MS`。`terminateActiveChildren` の消滅待ちと同じ）待つ。
   それでも確定しなければ、stdout / stderr の pipe と子の handle を解放して確定する（`close` を待ち続けない）。`confirmMs` は `ExecuteOptions` の任意の項目だけで、config・CLI オプションにしない
3. **打ち切りの結果**: グループが残っていれば、結果（`ExecutionResult`）に内部の任意の欄 `terminationUnconfirmed: { waitedMs, killError }` を付ける。グループが消えていて `close` だけが来ないとき（別のグループの孫が pipe を握っている）は付けない（こちらのグループは終了している）。
   この欄は `CheckResult`（レポートの JSON・Markdown）にはコピーしない
4. **文言**（`src/runner/run-checks.ts`）: 消滅を確認できたときは従来どおり `(process group terminated)`。確認できなかったときだけ、`(process group still present 2000ms after SIGKILL)`、
   シグナルを送れなかった（EPERM 等）ときは `(process group could not be signalled (EPERM) and was still present after 2000ms)`。数値と errno の識別子（`^[A-Z][A-Z0-9_]{1,15}$` に合うものだけ。他は `UNKNOWN`）以外の外部の文字列は入れない。
   `errorSummary` は従来どおりレポートの出口（ADR-0006・ADR-0016・ADR-0017・ADR-0020）を通る。中断の SKIPPED では、出力もシグナルも無くても、確認できなかったことは文言に出す（`ran` に含める）
5. **終了コードとレポートの欄は変えない**: 「消えていない」が付くのは、すでに FAIL（タイムアウト → 1）か中断（130 / 143）の経路だけ。EPERM の経路も、以前の `spawnError`（FAIL）から、タイムアウトの FAIL へ変わるだけで 1 のまま。
   「確認できなかった」を終了コード 2（ツールの異常）にはしない（1 → 2 の変化が生じ、CI の `== 1` の扱いを変えるため）
6. **kill の失敗（バックログ 2）**: グループへ送り、失敗（ESRCH 以外）なら子へ `process.kill(child.pid, signal)`（`child.kill()` は失敗を `error` イベントにするので使わない）。子へは、Node がまだ回収していない（`exitCode`・`signalCode` が null）間だけ送る。
   どちらにも送れなければ errno を覚え、決定 2 の打ち切りで `killError` に入れる。`child.on("error")` は、pid が無い（起動に失敗した）ときだけ `spawn failed` として確定する。起動の後の `error` は確定の理由にしない
7. **CLI の安全弁との関係**（v0.5.34 で表現を狭めた）: 既定では、猶予（5 秒）+ 確認（2 秒）= 7 秒 < 猶予 + 3 秒（8 秒、`SAFETY_VALVE_EXTRA_MS`。`src/cli-signals.ts`）で、**通常のスケジューリングでは、runner の既定の上限が安全弁より 1 秒短い**。
   そのとき中断の経路は、runner が先に確認を終えて返り、レポートを書いて終了する（以前は、別グループの孫が pipe を握ると安全弁で終了し、レポートは無かった）。
   **これは定数の関係で、レポートが先に書かれる保証ではない**: 安全弁はシグナル受信から固定で数え、runner の確認は SIGKILL のタイマーが実際に動いた時刻から（SIGKILL を送らないときは、消滅の最初の確認から）数える。
   レポートの書き込みは runner が返った後で、上限が無い。安全弁は最後の強制終了で、極端なイベントループの停止やレポート書き込みの遅れの下では、**レポートの完了前に発火しうる**
   （実測: 1.5 秒の停止で、安全弁が 8,018 ms に先に動き、レポートが書かれなかった）。そのときも終了コードはシグナル由来の非 0（130 / 143）のままで、fail closed は破れない。
   テスト（`DEFAULT_CONFIRM_MS` を export）が固定するのは「定数の関係」で、「レポートが先に書かれる」ことではない。後者を保証するには、確認の起点を予定時刻にする、または安全弁をフェーズごとの期限にする必要がある（採らなかった。下の代替案と ROADMAP の候補）
8. **変えないもの**: `terminateActiveChildren`（CLI は待たない。中断の確認は `executeCommand` が行う）、Windows の `groupAlive`（常に false の分岐。Windows は対象外で、macOS / Linux が対象）、ADR-0005 の他の決定
9. **消えたと分かった group には、以後何も送らない**（v0.5.34。独立レビュー R1・B16-R1-001）: 一度 ESRCH を見た（`kill(-pgid, 0)` でも、グループへのシグナルの送信でも）プロセスグループは、以後 signal 0 も SIGKILL も送らない。同じ数値が、OS により別のグループへ再利用されうるため。詳細は下の「範囲（v0.5.34 で追記）」。
   **v0.5.35 の補足**（独立レビュー R2・B16-R2-001）: グループ経路がある（POSIX で pgid がある）ときは、`gone` のグループの leader へも、子の pid への直接送信をしない。子へ直接送るのは、グループへの送信が ESRCH 以外（EPERM など）で失敗した、その呼び出しの中だけ（決定 6）。グループ経路が無い分岐（Windows・pgid なし）は、これまでどおり直接送る。詳細は下の「範囲（v0.5.35 で追記）」。
   **v0.5.36 の補足**（実装者が信号の経路の一覧の作成中に見つけた経路）: 子の pid への直接送信が ESRCH を返したら、その pid へは以後直接送らない（`GroupState.leaderGone`。1 度だけ立て、戻さない）。グループの `gone` と同じ規則を leader の pid にも当てる。グループ経路が無い分岐にも効く。詳細は下の「範囲（v0.5.36 で追記）」

## 範囲（v0.5.34 で追記）
- **きっかけ**（独立レビュー R1・B16-R1-001。High）: v0.5.33 の `poll()` は、グループの消滅を `goneAt` に記録するだけで、同じ番号へ signal 0 を 25 ms ごとに送り続けた。`close` が来ていないと SIGKILL のタイマーも残り、猶予が切れると、消えたと分かっているグループの番号へ SIGKILL を送った。
  `terminateActiveChildren` も、猶予の後に全 target へ SIGKILL を送った。番号が別のグループに再利用されていれば、無関係なプロセスグループへ SIGKILL が届く。この ADR の既知の限界は、これを「実際より悪い向きの誤り（「消えていない」と書くだけ）」と説明していた。**この説明は SIGKILL を落としていた**
- **v0.5.32 から同じ性質があった**（実測。`process.kill` の差し替えで、最初の ESRCH の後に同じ番号の別グループが応答する形を作り、決定的に再現した。実際の再利用は待っていない）
  **（v0.5.36 で訂正: ここでの「再現」は、差し替えで「同じ番号が別のグループとして応答する状況」を作り、そのとき runner が何を送るかを確かめたという意味で、実際の pgid の再利用は再現していない。下の既知の限界のとおり。実測は手元の実験〈「範囲（v0.5.36 で追記）」〉）**。v0.5.32 も、`close` 未着・`close` が先・最初のシグナルが ESRCH・`terminateActiveChildren`・既定値のすべてで、消えたグループの番号へ SIGKILL を送った
  （ESRCH を見ないまま送る形と、見た後に送る形）。v0.5.33 は、`close` が先に来る形では SIGKILL を送らなくなり（グループが消えたら確定する）、`close` 未着の待ちを有界にしたが、「消えたと分かっているのに送る」形が `close` 未着・`terminateActiveChildren`・最初のシグナルが ESRCH に残った。
  v0.5.33 が新しく SIGKILL を送る形は無い。増えたのは signal 0 の回数と、「消えていない」と誤って書く可能性
- **規則**: プロセスグループごとに `GroupState { pgid, gone }`（`src/runner/execute.ts`）を持ち、`activeChildren` に登録する。`gone` は、signal 0 または signal の送信が ESRCH になったとき 1 度だけ立て、**以後は戻さない**。`gone` のグループは、調べず（`groupAlive` は false を返す）、送らない（`killTree` はグループを飛ばす）。
  SIGKILL のタイマーは、`gone` なら何もしない（`sigkillSentAt` も設定しない）。**`executeCommand` の後始末と `terminateActiveChildren` は同じ記録を共有する**（どちらかが ESRCH を見れば、両方が以後触らない）
- **`close` 未着の待ち（決定 2・3 は変えない）**: SIGKILL のタイマーが発火する前にグループが消えたときは、消えたと分かった時点（`goneAt`）から最大 `confirmMs`。v0.5.33 のコードは、この形でも SIGKILL のタイマーが発火し、起点が SIGKILL を実際に送った時刻になっていた（文書の決定 2 とずれていた）。
  決定 9 で SIGKILL を送らなくしたので、起点が `goneAt` になる（短くなる。実測: 2.5 秒 → 1.7 秒、既定値で 7.0 秒 → 5.5 秒）。SIGKILL を送った後は、起点は SIGKILL の時刻のまま（v0.5.33 から変わらない）。
  **v0.5.34 のこの項は「消えたと分かった時点から」とだけ書き、SIGKILL が先の形を落としていた（v0.5.35 で訂正。下の「範囲（v0.5.35 で追記）」）**
- **Windows の分岐は変えない**: Windows（と pgid が無いとき）は、調べるグループが無いので `groupAlive` は ESRCH を見ずに false を返し、`gone` を立てない。SIGKILL のタイマーは送り（子の pid へ。グループの経路は元から飛ばす）、`killTree` も変わらない。
  対照テスト（`spawn` を差し替え、`process.platform` を `win32` にしたもの）で、`SIGTERM`・`SIGKILL` が子の pid に 1 回ずつ届くことを固定した。「win32 でも `gone` を立てる」誤った修正（変異）では、このテストが FAIL する。Windows は対象外（macOS / Linux が対象）
- **残る隙**（既知の限界）: (1) **最初のシグナルの前**: leader が先に終わり、`close` が来ないまま（別のグループの孫が pipe を握る）タイムアウトまでの時間が長いと、最初の SIGTERM は確認なしで番号へ送られる（その間に番号が再利用されうる）。実測で同じ性質を確認した（v0.5.32・v0.5.33・この版）。直さない（ROADMAP の候補）。
  (2) 最後の確認から送信までの 25 ms の窓（`kill` が持つ競合で、消せない）
- **安全弁との関係（B16-R1-002）**: 決定 7 の表現を狭めた（上のとおり）。実装の動きは変えない
- **テスト**: `tests/regression-backlog16-r1-pgid-reuse.test.ts`（6 件。最初の ESRCH の後に何も送らない、待ちの起点、最初のシグナルが ESRCH のとき、`terminateActiveChildren`、対照 2 件）と `tests/regression-backlog16-r1-win32-branch.test.ts`（1 件）。v0.5.33 の `src/` に当てると 4 件が FAIL（残りは対照）。
  不変条件は、`process.kill` の差し替え（記録した group にだけ効かせ、最初の ESRCH の後は同じ番号の別グループが応答するふりをする。実際の再利用は待たない）で決定的に検証する。待ちの起点のテストは時間に依存する（期待 1.9 秒、v0.5.33 は 3.0 秒、境界 2.6 秒）

## 範囲（v0.5.35 で追記）
- **きっかけ**（独立レビュー R2。B16-R2-001 High・B16-R2-002 Medium）: v0.5.34 の `killTree` は、`gone` のグループへの送信を飛ばしたが、そのまま下の「子の pid への直接送信」に落ちた。そのガードは `exitCode`・`signalCode` だけで、`gone` を見ない。
  `executeCommand` の後始末が ESRCH を見て `gone` を立てた後に、`terminateActiveChildren` が同じ `GroupState` で `killTree` に入ると、leader の pid へ SIGTERM が届きうる（CLI の中断は `abort()` の後に `terminateActiveChildren`。逆の順でも同じ）。v0.5.34 のテストの差し替えは負の id だけを見ていたので、検知できなかった。
  v0.5.33 は ESRCH で返っていた（v0.5.32 も）ので、**この経路は v0.5.34 の `!group.gone` が新しく開けた**（差し替えでの再現: v0.5.33 は正の pid へ 0 回、v0.5.34 は 2 つの順のどちらも SIGTERM 1 回）
- **規則**（決定 9 の補足）: グループ経路があるとき（POSIX で pgid がある）、`killTree` は、`gone` なら何も送らずに返る。成功したら返る。ESRCH なら `gone` を立てて返る。**子への直接送信に進むのは、グループへの送信が ESRCH 以外（EPERM など）で失敗した、その呼び出しの中だけ**。
  グループ経路が無い分岐（Windows・pgid なし）は、これまでどおり子の pid へ直接送る（そこは `gone` を立てないので、この規則の対象外）。直す場所は `killTree` の数行だけ
- **到達しやすさ（事実のみ）**: 実際の Node で、「`gone` かつ `exitCode === null` かつ `signalCode === null`」は、**観測されず、構造上も起きにくい**。macOS での確認: leader が終わって Node が回収していない間は、`kill(-pgid, 0)` は ESRCH にならず、EPERM（leader だけが残る形。`aiqh` は EPERM を「ある」と数え、`gone` にしない）か成功（孫が残る形）で、ESRCH になるのは回収の後。
  Node は、回収したのと同じコールバック（`ChildProcess` の `onexit`）の先頭で `exitCode` を設定する。`detached` の子は `setsid` で新しいセッションのリーダーなので、自分のグループから出ない。実際の子 360 個・約 77 万回の標本で、「ESRCH なのに `exitCode` が null」は 0 回だった（手元の実測で、再現の手順はリポジトリの外。Linux は未確認）。
  したがって、古いガード（`exitCode === null`）が実際には止めていたと見られ、**実害は起きにくい（推定。実際の実害は観測していない）**。**それでも直した**: 「グループが消えたと分かっているなら、何も送らない」方が単純で安全で、`exitCode` という別の事実に頼らないため
- **信号を送る経路の棚卸し**: `src/` の `process.kill`（signal 0 を含む）・`child.kill`・`spawn` 系の `timeout` を全部調べた（`docs/reviews/backlog-16-2-19/response-r2.md` の M3）。「ESRCH を見た後に届く」経路は、この 1 つ（`killTree` の直接送信）だけだった。`child.kill` の呼び出しは無い
- **B16-R2-002（文書の訂正。実装は変えない）**: v0.5.34 の範囲節・CHANGELOG・依頼文は、`close` 未着の待ちを「消えたと分かった時点（`goneAt`）から」と書いたが、コードは `anchor = sigkillSentAt ?? goneAt`（決定 2 の本文は元から正しい）。**正しくは**: SIGKILL のタイマーが発火する前にグループが消えたとき（SIGKILL は送らない。決定 9）は、消えたと分かった時点から最大 `confirmMs`。
  **SIGKILL を送った後は、SIGKILL を送った時刻から最大 `confirmMs`**（SIGKILL の後にグループが消えても、起点は SIGKILL のまま）。後者で `close` が未着のまま（別のグループの子孫が pipe を握る）のとき、全体の上限は SIGKILL + `confirmMs`。`GroupState` が共有するのは真偽値だけで、時刻は共有しない。
  文書の方が長く書いていたので、実際の上限は、文書より短いか同じ
- **実装を変えない理由**: 「SIGKILL が先で、その後にグループが消え、`close` が未着」の形は、別のグループの子孫が pipe を握るときに限られる。`GroupState` に時刻まで共有させる変更は大きく、得るものが小さい。起点は決定 2・7 のとおり
- **テスト**: `tests/regression-backlog16-r2-direct-signal.test.ts`（6 件）と `tests/regression-backlog16-r2-confirm-origin.test.ts`（1 件）。v0.5.34 の `src/` に当てると 2 件が FAIL（B16-R2-001 の 2 つの順）、5 件は対照・固定として PASS。
  差し替えは、記録した group の負の id と、同じ数の正の pid（leader）を見る。最初のグループへの送信を ESRCH にし、本物の leader は動かしたままにする（`exitCode` が null の状態。古いガードを通る）。起点の固定のテストは、SIGKILL の後の signal 0 を 1,000 ms「ある」と答えさせ、確定が SIGKILL の約 1,200 ms 後であること（消滅の確認から数えると約 2,200 ms。境界 1,700 ms）を固定する。起点を入れ替えた誤った実装（変異）で FAIL する
- **残る隙**（既知の限界。この版で変えない）: (1) 最初のシグナルの前（v0.5.34 のとおり）。(2) 最後の確認から送信までの 25 ms。
  (3) `terminateActiveChildren` は、複数の target のうち先の 1 つが生きている間、後ろの target を猶予の間調べない（`anyAlive` が `some` で短絡する）ので、猶予の後の SIGKILL が、実際には消えた後ろの target の番号へ届きうる。窓は猶予の全期間。CLI は同時に 1 つの子しか動かさないので到達しない（ライブラリとして並行に使う場合だけ）。ROADMAP の候補（項目 31）

## 範囲（v0.5.36 で追記）
- **きっかけ**: (a) 独立レビュー R3（`v0.5.34..v0.5.35`。High 0・Medium 0・Low 1。R2 の B16-R2-001・B16-R2-002 はどちらも解消と判定）の B16-R3-001。(b) v0.5.35 の実装者の自レビュー S-1〜S-6（独立ではない。`docs/reviews/backlog-16-2-19/response-r2.md`）。
  (c) **実装者自身が、v0.5.36 の信号の経路の一覧を作り直す途中で見つけた経路**（leader の pid。レビューの指摘ではない）。R1〜R3 のレビューのサイクルは、R3 で終えた（人間の判断。`response-r3.md`）
- **B16-R3-001（決定 6 の errno の保持）**: グループへの送信が ESRCH 以外（EPERM など）で失敗した後、子への直接送信が ESRCH になると、`killTree` は `null` を返してグループの errno を捨てていた（v0.5.33 から。`killTree` が errno を返すようになったのが v0.5.33）。
  グループは残っている（EPERM は「ある」と数える）ので、打ち切りの文言が「could not be signalled (EPERM)」ではなく「still present」になった。**今は、子が ESRCH のときはグループの errno を返す**（グループ経路が無い分岐では errno が無いので、これまでどおり null）。決定 6 の「どちらにも送れなければ errno を覚え」と一致する。変わるのは診断の文言だけで、status・verdict・終了コードは同じ
- **S-1（`terminateActiveChildren` の全対象の確認）**: `anyAlive` は、全 target を調べてから判定する（`some` の短絡をやめた）。猶予の間に消えた後ろの target も消えたと分かり（`gone`）、猶予の後の SIGKILL を受けない。上の「範囲（v0.5.35 で追記）」の残る隙 (3) を閉じた。
  確認と送信のあいだの窓は、`terminateActiveChildren` の確認の間隔（50 ms）に縮む（「最後の確認から送信まで」の窓と同じ性質）
- **leader の pid（決定 9 の v0.5.36 の補足）**: 記録していたのはグループの ESRCH だけで、子の pid への直接送信が ESRCH を返しても記録しなかった。グループへの送信が EPERM などで失敗し続けると、次のエスカレーション（SIGKILL のタイマー、`terminateActiveChildren`）で、**ESRCH を返した同じ pid へもう一度直接送った**（v0.5.33 から。差し替えでの再現: 中断だけなら pid へ SIGTERM〈ESRCH〉と SIGKILL の 2 回、CLI の中断の順〈`abort()` → `terminateActiveChildren`〉とその逆では SIGTERM 2・SIGKILL 2 の 4 回）。
  今は `GroupState.leaderGone` を、直接送信が ESRCH のとき 1 度だけ立て、以後その pid へは直接送らない（グループの errno は B16-R3-001 のとおり返す）。グループ経路が無い分岐（Windows・pgid なし）にも効く: Windows で子の pid が ESRCH を返したら、以後その pid へ送らない（Windows は対象外。`spawn` を差し替えた Windows の対照テストは、直接送信が成功する形で、変わらない）
  **（R4 の後に訂正: 「グループ経路が無い分岐（Windows・pgid なし）」は「Windows」が正確。pgid が無いのは `child.pid` が無いとき〈起動できなかったとき〉だけで、そのときは直接送信の前のガード〈`child.pid === undefined`〉で、もともと何も送らない。`leaderGone` が実際に効くのは Windows の分岐。動きの説明は変わらない）**
- **leader の pid の到達しやすさ（推定。v0.5.35 の「到達しやすさ」と同じ構造）**: 実際の Node でこの経路に入るには、子の pid が ESRCH を返し、かつ `exitCode`・`signalCode` が null である必要がある。回収前の leader への `kill(pid, …)` は成功し（v0.5.35 で macOS を確認）、Node は回収したのと同じコールバックの先頭で `exitCode` を設定するので、JS からは見えないと見る。
  この版では実測していない。B16-R3-001 も、同じく差し替えでしか作れない状態の上の話。それでも「消えたと分かっている番号へは何も送らない」を、負の pgid と正の pid の両方で成り立たせるために直した
- **信号を送る・調べる経路の棚卸し（v0.5.36）**: `docs/reviews/backlog-16-2-19/response-r3.md` に、`grep` のコマンドと出力をそのまま載せた（R3 の未確認範囲 5 への答え。変更していない `review/packet.ts`・`git/info.ts`・`cli.ts`・`cli-signals.ts`・`scripts/test-minimal-path.ts` を含む）。
  **ESRCH を見た後に、番号（負の pgid・正の pid）へ何かが届く経路は 0**。timeout の無い `git` の `execFileSync`（`commands/init.ts`・`security/scan.ts` の 3 か所）も一覧に足した（シグナルを送らない）
- **記述の訂正（自レビュー S-5）**: 上の「範囲（v0.5.34 で追記）」の「決定的に再現した」に、訂正の注記を入れた（実際の pgid の再利用は再現していない）。`response-r1.md` は本文を変えず、末尾に訂正の節を足した
- **手元の実測であること（自レビュー S-6。1 か所にまとめる）**: この ADR と `docs/reviews/backlog-16-2-19/` の実測のうち、次はすべて **git 管理外の手元の実験**（macOS、Node 24.13.1）で、実験のスクリプトはリポジトリに入れていない。リポジトリ・レビューパケットからは検証できない。

## 代替案
- 文言・コメント・文書だけを「送った」までの主張に直す: 無限待ちが残る（20 秒返らなかった）。確認できたときも文言が変わり、既存テスト 1 件（`regression-m2-2-flake-001-timeout-after-abort.test.ts`）の期待値が変わる。採らない
- 確認できなかったときに終了コード 2: 上の決定 5 のとおり採らない
- 有界時間を 1,000 ms にする: 安全弁との余裕は増えるが、遅い環境で、実際には消えるものを「消えていない」と書きやすい。3,000 ms 以上は中断の経路で安全弁が先に動く
- 有界時間を設定項目にする: 設定の契約を増やす（M2-2 の範囲外）。`ExecuteOptions` の任意の項目だけにした
- EPERM のとき `error` を握りつぶすだけ（`child.kill` のまま）: 早い確定は直るが、`close` が来ないときの無限待ちが残る。有界時間とセットで直す
- 子へのシグナルを `process.kill` に変えるだけで有界時間を足さない: EPERM のとき永久に待つ。**kill の失敗の扱い（決定 6）は、有界時間（決定 2）に依存する**
- （v0.5.34）`executeCommand` の中だけに記録を持ち、`terminateActiveChildren` には別の記録を持たせる（レビューの案）: 同じ規則が 2 か所になり、片方の直し忘れが起きうる。SIGKILL のタイマーの「解除」には「エスカレーション済み」の別の印が要る（`killTimer !== null` がその印）。共有の記録にして、タイマーは「発火したら何もしない」にした
- （v0.5.34）送る直前に、もう一度 signal 0 で確かめる: 再利用された別のグループは「生きている」と答えるので、効かない
- （v0.5.34）leader の開始時刻などでグループを同定する: `ps` などの外部コマンドが要り、最小 PATH の前提と OS 差の問題がある。採らない
- （v0.5.34）安全弁の起点を予定時刻にする（確認の起点を、SIGKILL を実際に送った時刻でなく、中断の受付 + 猶予にする）: 実測で、1.5 秒の停止なら 7,044 ms でレポートが書かれた。ただし 3 秒以上の停止は防げず、遅れた後の確認が `confirmMs` より短くなる。レポートの書き込みの上限も残る。採らない
- （v0.5.34）安全弁をフェーズごとの期限にする（runner の確認の完了の後に、レポート用の期限を数え直す）: 書き込みにも上限を持てるが、安全弁の意味（最後の強制終了）が変わり、`cli.ts` と verify の流れを変える（`cli.ts` の最上位の項目 20 と衝突しうる）。採らない。ROADMAP の候補

## 既知の限界
- **別のプロセスグループへ移った子孫（`setsid` 相当）は止められない**: aiqh が止めるのは、チェックのプロセスグループだけ。確定しても、その子孫は残る（実測: 寿命 10 秒の孫は、返った後も約 10 秒生きた）。決定の対象外
- 通常に終わった（終了コード 0 など）チェックの後に、同じグループに残った子孫は見ない（確認は、タイムアウトと中断の後だけ）
- 打ち切りの後に出た stdout / stderr は取らない（別のグループの孫が pipe を握っているときなど）。取得済みの出力（末尾）はそのまま `stdoutTail` / `stderrTail` に入る
- **`kill(-pgid, 0)` もグループへのシグナルも、同じ番号の別のグループがあれば、そちらに届く（pgid の再利用）**: 別のグループは「ある」と答え、signal 0 以外は別のグループへ届く。v0.5.33 までは、消えたグループの番号へも SIGKILL を送った（v0.5.32 から同じ性質があった。v0.5.33 の版のこの項は、
  「2 秒待って『消えていない』と書くだけの、実際より悪い向きの誤り」と説明していたが、SIGKILL が届きうる点を落としていた）。v0.5.34 の決定 9 で、一度 ESRCH を見たグループへは何も送らなくした。残る隙は、最初のシグナルの前と、最後の確認から送信までの 25 ms（上の「範囲（v0.5.34 で追記）」）、`terminateActiveChildren` が後ろの target を猶予の間調べない形（「範囲（v0.5.35 で追記）」。v0.5.36 で閉じた）。
  EPERM は「ある」と数える。実際の pgid の再利用は再現していない（pid は毎秒約 830 進み、1 周は約 2 分。差し替えで決定的に確かめた）
- **Windows**（v0.5.37 で記録。ROADMAP の M3「Windows での挙動確認」。Windows は対象外）: `groupAlive` は常に false なので、`close` が未着でも最初のポーリング（25 ms）で `goneAt` が入り、`confirmMs` の後に確定する。既定値（猶予 5 秒・確認 2 秒）では猶予より先に確定し、SIGKILL のタイマーは解除される。Windows の SIGTERM は強制終了で leader は止まるが、子孫はグループが無いので止めていない（どの版も同じ）。そのときの `errorSummary` の「process group terminated」は正確ではない
- 確認の粒度は 25 ms。通常の SIGKILL の経路は +10 ms 前後（実測: 中央値 2,505 → 2,517 ms）。1 回、負荷の下で 2,784 ms を観測した
- 本物の EPERM は再現していない（通常ユーザーで安全に起こせない）。EPERM の挙動は、同じプロセスの中の模擬（`process.kill` と `ChildProcess.prototype.kill`）で確かめた
- テスト「SIGKILL の経路: 返った時点でグループが消えている」は、v0.5.32 では結果が決定的でない（グループは SIGKILL の数 ms 後に消えるため）。この版以後に PASS し続けることを守るガードで、v0.5.32 での FAIL は保証しない
