# ADR-0022: 読めないものを「無い」としない: パスの包含と書込の前提

- 状態: 採用（ADR-0010・ADR-0015 の「ENOENT だけが無い」を、設定のパスの包含判定と init の書込の前提へ広げる。v0.5.30 で B グループ（P3・P11・P4）へ、v0.5.31 で C グループ（O3・O4・O5・O9）へ、v0.5.32 で D グループ（O6）へ広げた（バックログ 8 は完了）。ADR-0014・0015・0020・0021 は変えない）
- 日付: 2026-10-04（M2-2、v0.5.29。ROADMAP のバックログ 8 の A グループ: O2・O7・O8）。追記: 2026-10-04（v0.5.30。B グループ: P3・P11・P4）、2026-10-05（v0.5.31。C グループ: O3・O4・O5・O9）、2026-10-05（v0.5.32。D グループ: O6）、2026-10-11（v0.5.37。バックログ 26・24・25・23）

## 文脈
- 原則は既にある: security-scan の lstat（ADR-0010、M1-R2-002）、review-packet の `latest.json` と既定の設定ファイル（ADR-0015、v0.5.1）。**ENOENT だけが「無い」**で、それ以外は読めない・見えないものなので fail closed にする。
  v0.5.1 の洗い出し（`docs/reviews/m2-2/response-r1.md`）が、同じ形の残りを 11 項目（O・P）に分けてバックログ 8 とした。A グループはそのうち書き込み・パスの判定に関わる 3 つ（O2・O7・O8）
- 実測（v0.5.28。実際の CLI。ROADMAP の記述は「コード読解」だったものを再現した）:
  - **O2**: `src/config/load.ts` の `entryExists()` が lstat の失敗をすべて「無い」とし、`realpathNearest()` が親へ上がる。権限で辿れないディレクトリ（EACCES）や通常ファイル（ENOTDIR）の下の `cwd`・`output.dir` が、読込を通る。
    辿れないディレクトリの中に根の外を指す symlink があっても「プロジェクトの中」と判定する。結果は、`cwd` は check の FAIL（exit 1、"working directory does not exist"）、`output.dir` は check を全部走らせた後の report write error（exit 2）。
    外への書き込みは 0 件だった（辿れないので、後の mkdir と cwd の起動が失敗する）
  - **O7・O8**: `existsSync()` は dangling symlink（リンク先が未作成）で false になり、init は「作る」と判断する。`writeFileSync()` は symlink を辿ってリンク先を作る。`init --write` と `--write-gitignore` が、プロジェクトの外にもファイルを作り、
    `wrote …` と表示して exit 0 だった（`--force` でも、リンク先が根の中でも同じ）
  - 対照（変わらないこと）: 未作成の `output.dir`、存在しない `cwd`（CONFIG_SPEC §4 の 7: 読込は通り、その check が FAIL）、根の中を指す symlink、dangling symlink 越しの `output.dir`（v0.5.28 でも拒否）、symlink の輪での書込（ELOOP で失敗）
- **B グループ（v0.5.30 で追記。P3・P11・P4）**: 同じ形の残りのうち、入力や後片付けの失敗を「無い」「あった」として扱っていた 3 つ。v0.5.29 のコードの形:
  - **P3**: `resolveCommit()`（`src/review/packet.ts`）は git を 2 回呼ぶ。1 回目（`<ref>^{commit}`）は status を見るが、2 回目（ref 自身。tag object を得る）は status を見ず、失敗を「tag object が無い」として packet を書く（exit 0）。
    ref が 2 回の呼び出しの間に動くと、別の commit に属する tag object が載る
  - **P4**: 書込の失敗の後片付け（`removeTmps()`、`src/commands/review-packet.ts`）は `existsSync()` で一時ファイルを探す。辿れない一時ファイルは false になり、消されず、「temporary file left at」にも挙がらない（残っているのに exit 2 のメッセージが何も言わない）。
    rename で正しい場所へ入った一時ファイルも、マップに残っていた
  - **P11**: `readVersion()`（`src/cli.ts`）は、`package.json` が読めない場合も、version が無い場合も `"0.0.0"` を返す（文字列でない version はそのまま通る）。この値は `--version`、verify のレポートの `tool.version`、review packet の「Generated by」に書かれる＝作った道具の身元の証拠になる

## 決定
1. **規則**: ENOENT だけが「無い」。lstat・stat の他の失敗（EACCES・ENOTDIR・ELOOP など）は「調べられない」で、「無い」と見なさない。dangling symlink は lstat では「ある」（リンク自体がある）。リンク先が無いことは「無い」ではない
2. **パスの包含判定**（`resolveInsideRoot` → `realpathNearest` → `entryExists`。`checks[].cwd` と `output.dir`）: ENOENT だけ、存在する最も近い祖先へ上がる。他の失敗は `ConfigError`
   （`<label> cannot be resolved: <path> — <entry> cannot be examined (<code>). Fix the permissions or change the setting.`。`<entry>` が `<path>` と同じときは `— <entry>` を付けない: v0.5.31 で重複を解消）。設定を読む時点のエラーなので、check は 1 つも走らず、レポートも書かない。終了コードは 2
3. **init の書込の前提**（`src/commands/init.ts` の `assertNotDanglingLink`）: 書込先が symlink で、リンク先が ENOENT（dangling）のとき、書かずに拒否する。lstat でリンクかを見て、リンクなら stat で先を見る。
   設定の書込（`aiqh init: failed to write <file>: …`）と `.gitignore` の追記（`aiqh init: failed to update <file>: …`）の、既存の `try` の中で、書込の直前に呼ぶ。メッセージは `it is a symbolic link whose target does not exist; remove the link or create the target first`。
   lstat・stat の ENOENT 以外の失敗は、そのまま投げる（書込自身のエラーと同じ形で報告される）。**`--force` でも拒否する**（上書きする既存の内容が無い）。終了コードは 2。
   書く内容・書く関数（`writeFileSync`）・外側の関数（`runInit`）は変えない（書き込み箇所の一覧テストの表も変わらない。ADR-0020 決定 7）。設定と `.gitignore` の書込は独立のまま（一方が拒否されても他方は取り消されない。CONFIG_SPEC §5.3c）
4. **ENOTDIR も拒否する**（O2）。通常ファイルの下には何も存在しえないので、判定そのものは健全で、「無い」と扱う案も成り立つ（推論）。それでも拒否にする理由: (a) 「ENOENT だけが無い」を、文書（ADR-0010・0015、ARCHITECTURE、CONFIG_SPEC）のとおり文字どおりに守る。例外を 1 つ作ると、
   B・C・D の各箇所で ENOTDIR の扱いを問い直すことになる。(b) 通常ファイルの下を `cwd`・`output.dir` に指定する設定の誤りを、実行時の check の FAIL（cwd は exit 1）や遅い report write error ではなく、読込で exit 2 にして早く見せる。
   **`targetIdentity`**（`src/commands/review-packet.ts`。review-packet の書込先の同一性を、存在する祖先まで遡って比べる）は ENOENT と ENOTDIR を「無い」として親へ上がるが、そのまま残す: 目的が違い（書込先の早い段階の拒否。最終判定は dev + ino）、
   ENOTDIR は書込の本体が失敗するので判定を誤らせない。この ADR の規則は、設定のパスの包含判定と init の書込の前提に適用する
5. **範囲外**（直さない）: 有効な symlink への `--force` 上書き・追記（プロジェクトの外の既存ファイルにも書く）は、ROADMAP のバックログ 23（**v0.5.37 で、root の外を指すものは拒否にした**。範囲〈v0.5.37〉）。バックログ 8 は v0.5.32 で完了した（P3・P11・P4 は v0.5.30 で、O3・O4・O5・O9 は v0.5.31 で、O6 は v0.5.32 で直した。決定 7・8・9 と「範囲（B グループ）」「範囲（C グループ）」「範囲（D グループ）」）
6. **出力の境界は変えない**: 新しいメッセージは既存の出口を通る（init は `output.error`、verify は `maskSecrets` の後に出口。ADR-0016・0017）。パスに禁止文字や秘密の形があっても、表記とマスクになる（実 CLI で確認）
7. **必須の入力は、ENOENT でも既定値にしない**（P11、v0.5.30）。`package.json` が無い（ENOENT を含む）・読めない・version が文字列でない・空文字、のいずれも**失敗（exit 2）**で、`0.0.0` などの既定値にしない。version は**最初に読み、すべての入口を止める**（`--version`・`--help`・`init`・`verify` のどれも exit 2）。
   既存の最上位の catch を再利用する（`aiqh: unexpected error: cannot read the version from package.json (<code>)` または `… package.json has no version string` と `VERIFY ERROR (internal error)` の 2 行）。専用のメッセージ・終了コードは作らず、`src/cli-program.ts` も変えない。
   「無くても動ける入力」と「無ければ証拠が偽になる入力」を区別する規則で、後者（version は、レポートと packet に作った道具として書かれる）だけが対象
8. **git が答えた「違う」と、git の失敗を分ける**（O3、v0.5.31）。git に尋ねる箇所では、次の 2 つだけを git の「違う」とする: (a) `rev-parse --verify --quiet` の exit 1（名前が無効のとき、何も出さずに終わる）、(b) `rev-parse --is-inside-work-tree` が exit 0 で `false`、
   または exit 128 で stderr の 1 行目（`LC_ALL=C`）が `fatal: not a git repository` で始まる。**それ以外**（git を実行できない〈spawn のエラー〉、timeout、他の status）は git の失敗で、「違う」「無い」とは書かない。
   verify（`src/git/info.ts` の `lookupGit`。`getGitInfo` は同じ署名で残す）: 失敗のとき標準出力は `git: unavailable (<理由>)`（`git could not be run (<code>)`・`git timed out after 10 s`・`git exited <N>: <git の 1 行>`）、「違う」のとき従来の `git: not a git repository`。
   **報告の JSON の `git` は、どちらも null のまま**（契約は変えない。理由を持つのは標準出力の行だけ）。Markdown のセルは `(not a git repository, git unavailable, or no commit)`（報告に理由の欄が無いので、言い過ぎない文面）。
   review-packet（`resolveCommit` と work-tree の確認。B の P3 が回した「失敗の文言」を引き取る）: 「違う」のときは従来の文（`does not name a commit`、`not inside a git work tree: <cwd>`）、それ以外は git の言葉を添える
   （`--range: <side> revision "<ref>" could not be resolved (git exit N: <git の 1 行>)`、`could not tell whether <cwd> is inside a git work tree (git exit N: <git の 1 行>)`）。git を実行できないことは元から `git could not be run: …` で区別されている。終了コードは 2 のまま。
   「違う」の判定は終了コードと stderr の 1 行の文言（`LC_ALL=C`）に頼る。文言が変わったときは、「違う」が失敗の側に倒れる（見える側）だけで、失敗が「違う」に隠れる方向ではない
9. **アダプタの入口は、ENOENT だけ「無い」**（O6、v0.5.32）。アダプタが見る `RepoContext`（`src/adapters/context.ts`）の `exists()`・`readText()`・`listTopLevel()` は、ENOENT だけを「無い」とする。読みの ENOENT でも、lstat で入口があれば（dangling symlink）「調べられなかった」であって「無い」ではない。
   通常ファイルの下の入口（ENOTDIR。`tests` が通常ファイルのときの `tests/e2e`）も、決定 4 と同じく「調べられない」。読めたが JSON として解釈できない `package.json`（マージの衝突の跡など）も、「Node ではない」と見なさず失敗として扱う。
   **実行できない入口は別**: x ビットが無い・dangling な venv の python などは、調べられなかったのではなく、そのものの性質。`isExecutable()` は、lstat で入口の有無を分けたうえで、実行できなければ false のまま（既存の `venvPresentButUnusable` の扱いが受ける）。
   調べられない入口があるとき、`ExaminationError`（`src/adapters/context.ts` から export。`<entry> cannot be examined (<code>)`・`<entry> is a symbolic link whose target does not exist`・`<entry> is not valid JSON`・`the top-level entries cannot be listed (<code>)`）を投げ、
   `aiqh init` は監査を止めて `aiqh init: cannot audit <root>: <entry> …` で **exit 2**（dry-run も。何も監査せず、何も書かない）。アダプタは検出するときに入口を遅延して調べるので、例外は `buildRepoContext` と `resolveDetections` の両方から出る。`RepoContext` の型は変えない（ADR-0011 の境界は変わらない）。
   例外にする理由: 新しいアダプタや新しい入口も、`exists()`・`readText()` を使うだけで自動で対象になる（理由を集める案は、呼び出し側が毎回確かめる必要がある）。root が辿れない（0600）ときの文言は、最初に調べた入口の名前が出る（`cannot audit <root>: package.json cannot be examined (EACCES)`。`describeRootProblem` は変えない）

## 範囲（B グループ、v0.5.30 で追記）
- **P3（git の失敗は「無い」ではない）**: `resolveCommit()` は、ref を **1 回だけ**オブジェクト名に引き（`rev-parse --verify --quiet --end-of-options <ref>`）、その `<オブジェクト名>^{commit}` で commit を求める。2 回とも status を見て、失敗は `does not name a commit`（文言は v0.5.29 のまま）で exit 2。
  commit はオブジェクト名から求めるので、ref が動いても tag object と commit は別の状態から来ない。オブジェクト名が commit と違うときだけ tag object として載せる。通常の入力（tag なし、軽量 tag、注釈付き tag、SHA）の packet は、バイト単位で v0.5.29 と同じ（実測: v0.5.29 の `src/` と比べ、注釈付き tag・軽量 tag・SHA・`HEAD~1`・tag 同士・`^{commit}` 付きの 6 つの range で一致）
- **P4（後片付けの `existsSync` をやめる）**: `removeTmps()` は `rmSync(t, { force: true })` だけにする（`force` が無視するのは ENOENT だけ）。消せない一時ファイルは `left` に入り、「temporary file left at」に挙がる。rename で確定した一時ファイルはマップから外す（`tmps.delete(t)`、1 行）。
  外した後は、確定したファイルが「残った一時ファイル」として挙がらない
- **P11**: 決定 7

## 範囲（C グループ、v0.5.31 で追記）
- **O3**: 決定 8。v0.5.30 では、git を実行できない・timeout・exit 128（所有者の不一致など）が、verify の標準出力で `git: not a git repository`、review-packet の ref の解決で `does not name a commit`（status 1 と同じ文）と書かれた（実測。verify はどれも exit 0 で、verdict は変わらない）。
- **O4**（`checkDirectory`、`src/runner/execute.ts`）: ENOENT だけ `working directory does not exist: <dir>`、他の stat の失敗（EACCES・ENOTDIR・ELOOP など）は `working directory cannot be examined: <dir> (<code>)`。A（v0.5.29）の後は、読込が辿れない `cwd` を拒否するので、
  ここに届くのは読込の後でパスが変わった場合（check が権限を変える、ディレクトリを置き換える、symlink の輪を作る）。check は起動せず FAIL のまま（verify は exit 1。ENOENT と同じ）。
- **O5**（`proposeGitignore`、`src/commands/init.ts`）: `.gitignore`・`.git` の `existsSync` を lstat の判定にする。ENOENT だけ「無い」（`no .gitignore`、`not a git repository: cannot ask git …`）。リンクは「ある」（dangling や輪でも。git が判断する）。
  他の失敗は `.gitignore cannot be examined (<code>): cannot confirm; add the line if it is missing`、`.git cannot be examined (<code>): cannot ask git whether artifacts/ is ignored`。dry-run の終了コードは 0 のまま。
  v0.5.30 では、dangling・輪の `.gitignore` が `no .gitignore`、dangling の `.git` が `not a git repository` と書かれ、同じ実行の audit の行（`git repository; …`）と食い違っていた。
- **O9**（`runInit` の root、`src/commands/init.ts`）: root を stat で分類する。ENOENT だけ `directory not found: <root>`、他の失敗は `directory cannot be examined: <root> (<code>)`、ディレクトリでなければ `not a directory: <root>`。いずれも exit 2。
  **通常ファイルの root は、exit 0（ファイルをリポジトリとして監査していた）から exit 2 になる**。dangling symlink の root はリンク先が ENOENT なので `directory not found`。
- **O2 の文面の重複**: 決定 2。`<entry>` が `<path>` と同じとき `— <entry>` を付けない。dangling symlink の文（`… is a symbolic link whose target does not exist …`）も同じ形で直した。
  既存テストの期待値 1 件を変えた（`tests/regression-backlog8a-o2-untraversable-path.test.ts` の、EACCES の `output.dir` の正規表現。人間の承認）。
- 触っていない同種の箇所: init の書込側の `existsSync`（設定ファイルの already exists、`.gitignore` の読み出し）は、A の dangling の拒否と書込の失敗が受けるので変えない（実測で影響なし）。`src/adapters/context.ts` の `exists()`・`readText()` は D（O6）で、v0.5.32 で直した（「範囲（D グループ）」）

## 範囲（D グループ、v0.5.32 で追記。バックログ 8 の最後）
- **O6**（`src/adapters/context.ts`、`src/commands/init.ts`）: 決定 9。v0.5.31 では、`package.json` が読めない（EACCES）・dangling symlink・symlink の輪・ディレクトリ・不正な JSON のどれでも、`init` の出力は `package.json` が本当に無いときと同じだった
  （exit 0、`project: … (other)`、Node の検出はすべて `not-applicable`）。`tsconfig.json`・`pyproject.toml`・`requirements*.txt`（root の一覧）・root の入口が調べられないときも同じだった（実測）。
- **影響の広さ**: 検出の入口が隠れるので、`init --write` が書く設定から check が消えた（dangling または不正な JSON の `package.json` では `security` だけ。その設定の `aiqh verify` の判定が、健全なときの FAILED から PASSED に変わった。実測）。
  `--write-scripts` は何も言わずに exit 0 で終わった。アダプタは `init.ts` と `config/generate.ts` からしか使われないので、`verify`・`security-scan`・`review-packet` の判定には直接関わらない。
- 変更後は、調べられない入口があるとき `init` が exit 2 で止まる。dangling な `.git` の提案と audit は C で揃っていて変わらない（lstat。`.git` は「ある」）。

## 範囲（v0.5.37 で追記。バックログ 8 の範囲外として残した項目）
- **バックログ 26**（`src/adapters/context.ts` の `buildNode`）: 決定 9 を、JSON としては正しいが形が違う `package.json` へ広げた。トップが JSON のオブジェクトでないとき（`null`・配列・文字列・数値・真偽値）は `package.json is not a JSON object`、`scripts`・`dependencies`・`devDependencies` があってオブジェクトでないとき（`null` を含む）は `package.json has a "<field>" field that is not a JSON object` の `ExaminationError` にする。
  v0.5.36 では、`null` と `scripts` が数値は生の TypeError（`aiqh: unexpected error: …`、`VERIFY ERROR (internal error)`。exit 2）、配列・文字列・数値は空の `package.json` として Node プロジェクト扱い（exit 0）だった。今は `init` が `cannot audit <root>: …` で exit 2 で止まる。`name` の型は見ない（数値の `name` は、`--write` の設定の検証が拒否する。v0.5.36 と同じ）
- **バックログ 24**（`src/security/scan.ts` の `listFiles`）: `git ls-files` が失敗したとき、root を `statSync` で調べ、root の問題なら init の root（O9）と同じ文言で言う: `directory not found: <root>`（ENOENT）、`not a directory: <root>`、`directory cannot be examined: <root> (<code>)`。root がディレクトリなら、従来どおり `not a git repository (or git failed): …`（git が PATH に無いときも）。終了コードは 2 のまま。
  v0.5.36 では、存在しない `--cwd` も、通常ファイルの `--cwd`（`--config` を別に指定して設定の読み込みを通したとき）も、git の失敗として言っていた。正常な root では stat を足さない（失敗したときだけ見る）
- **バックログ 25**（`src/git/info.ts`・`src/commands/verify.ts`）: 決定 8 の「git の答えと失敗を分ける」を、コミットとブランチにも広げた。実装の前の実測（git 2.50.1）: コミットが無いとき `rev-parse --verify --quiet HEAD` は何も出さずに exit 1、detached HEAD で `symbolic-ref -q --short HEAD` は exit 1、本当の失敗（リポジトリでないなど）は exit 128。stderr の判定は要らない。
  exit 1 は git の答え（`(no commit)`、detached なら従来どおり `rev-parse --abbrev-ref HEAD` の `HEAD`）、それ以外の終了・起動の失敗・時間切れは失敗で、verify の `git:` の行に `(commit: unknown)`・`(branch: unknown)` と出す（`(dirty: unknown)` と同じ形）。**レポートの `git` は形も値も変えない**（失敗は null のまま。O3 と同じ判断）。v0.5.36 では、失敗も `(no commit)`・`(detached)` と表示していた
- **バックログ 23**（と、SP1 で見つけた N1。`src/commands/init.ts` の `assertLinkInsideRoot`）: 決定 3 を広げた。3 つの書込先（`aiqh.config.jsonc`・`.gitignore`・`--write-scripts` の `package.json`）は、dangling の拒否の後、リンクを解決した先（`realpath`）が root の `realpath` の外なら、書かずに拒否する（決定 3 と同じ形: `failed to write …` / `failed to update …: it is a symbolic link to <target>, outside the project root; …`、exit 2。`--force` でも拒否）。
  root の中を指す symlink は、従来どおりリンク先に書く（dotfile の管理などで、プロジェクトの中の共有ファイルへ向けている使い方は壊さない）。`--write-scripts` は `--force` なしでも書き、symlink の検査が何も無かった（N1）ので、dangling の拒否も揃えた。
  既存テストの期待値を 1 件変えた（人間の承認）: `tests/regression-backlog8a-o7-o8-init-dangling-link.test.ts` の「外の既存の `.gitignore` への symlink に追記できる」（最小の変更の境界の確認）は、exit 2 で外のファイルが変わらない、に変えた

## 代替案
- ENOTDIR を「無い」とする（O2 の 1 行差）: 決定 4 の理由で採らない。実測では、通常ファイルの下の `output.dir` は v0.5.28 と同じ挙動のまま（遅い exit 2）、`cwd` も同じ（check の FAIL、exit 1）になる
- dangling 以外の symlink も拒否する（すべての symlink 経由の書込、または根の外を指す symlink のみ）: `.gitignore` を共有ファイルへの symlink にしているなどの既存の使い方を壊す。O7・O8 の原因は「リンクなのに存在確認が false になる」ことなので、dangling に限る最小の変更で直る。有効な symlink は別の項目（**v0.5.37 で、root の外を指すものだけを拒否にした**: バックログ 23。すべての symlink を拒否する案は、root の中の共有ファイルへのリンクを壊すので採らない）（バックログ 23）にした
- `writeFileSync()` の flag `"wx"`（排他的な作成）: dangling でも EEXIST で失敗し、lstat と書込の間の競合も無いが、`--force` の経路（上書き）には効かず、理由が open のエラーになる。先に lstat で理由を言えるほうを採る
- 共通の補助関数にまとめる（`load.ts` の `entryExists`、`review-packet.ts` の `lstatOrNull`、init の補助関数）: 判定の置き方（無い／投げる／拒否）が箇所ごとに違う。B・C・D で箇所が揃った後に検討する
- ADR を作らず CONFIG_SPEC・ARCHITECTURE・ADR-0015 に追記する（v0.5.1 の R1-007 と同じ流儀）: 利用者に見える契約（`cwd` の exit 1→2、init の拒否）を変え、原則が複数の ADR・文書に散らばっているので、B・C・D が参照する 1 か所を作った
- （B グループ）version が読めないとき `0.0.0` などの既定値のまま動く（警告だけ出す）: レポートと packet に書かれる道具の身元が偽になる。ENOENT でも既定値にしない（決定 7）
- （B グループ）version 専用のメッセージ・終了コード、`cli-program.ts` での検査: 新しい出口を作らずに、既存の最上位の catch（exit 2、2 行）で足りる。入口ごとの検査は、`--help`・`init` が漏れる形になりやすい
- （B グループ）`packet.ts` に git の呼び出しの差し替えの継ぎ目を足す: テストのためだけの境界が本体に残る。PATH の先頭に置いた `git` の shim で、本体を変えずに失敗と ref の移動を作れる

## 既知の限界
- **有効な symlink への `--force` 上書き・追記は、プロジェクトの外の既存ファイルに書く**（実測: `aiqh.config.jsonc` が外の既存ファイルへの symlink なら `--force` で上書き、`.gitignore` が外の既存ファイルへの symlink なら追記）。直していない（ROADMAP のバックログ 23）（**v0.5.37 で解消**: root の外を指すものは拒否する。`--write-scripts` も同じ。範囲〈v0.5.37〉）
- init の書込は、元から非原子的な `writeFileSync()` で、lstat と書込の間の競合（TOCTOU）は防がない（対話の道具・ローカルの実行が前提）
- 読込の後に権限が変わった場合は、実行時の失敗（check の FAIL、report write error）として残る
- Linux・Windows・root での実行は未確認（実測は macOS の一般ユーザーだけ。権限のテストは root では `skipIf`）。エラーコードの名前は POSIX 共通だが、Linux での挙動は推測
- dry-run の提案文（`proposeGitignore` の `existsSync(".gitignore")`）は、dangling でも「no .gitignore」と書き、書込時に初めて dangling と拒否した（O5。**v0.5.31 で解消**: lstat で判定する。dangling・輪の `.gitignore` の dry-run の説明は git の判断のもので、リンクの状態そのものは書込のときの拒否が言う）
- `package.json` が dangling symlink のとき、init は Node プロジェクトと見なさず、`--write-scripts` は exit 0 で何も書かなかった（実測。アダプタの検出。O6。**v0.5.32 で解消**: 調べられない入口があると `init` は監査を止めて exit 2 にする。決定 9）
- （B グループ）version は「空でない文字列」かどうかだけを見る。semver として妥当かは見ない（決定 7）
- （B グループ）辿れない一時ファイルは、消せずに残り、名前が挙がるだけ（P4）。消すのは人。ファイルを消せるかどうかは `rmSync` の結果に従い、「ある」ことの確認はしない
- （C グループ）**`rev-parse HEAD`・ブランチの個別の失敗は、`(no commit)`・`(detached)` と表示される**（verify の `git:` の行と報告）。コミット 0 件の本物のケースと区別するには、stderr の判定が要る。直していない（ROADMAP の項目 25）（**v0.5.37 で解消**: 終了コードだけで区別でき、stderr の判定は要らなかった。範囲〈v0.5.37〉）
- （C グループ）verify の報告の JSON の `git` は、非リポジトリと git の失敗のどちらも null で、理由は標準出力の行にだけある（Markdown のセルは両方を含む文面）。理由を報告に載せるには新しい欄（契約の変更）が要るので、していない
- （C グループ）git の「違う」の判定は `fatal: not a git repository` の文言に頼る（決定 8）。他の言語・他の git の実装での文言は未確認（`LC_ALL=C` で固定している）
- （C グループ）`security-scan --cwd <存在しないディレクトリ>` は、cwd の ENOENT を git のせいに見せる（`not a git repository (or git failed): … (spawnSync git ENOENT)`）。init の root（O9）と同じ形で、root の分類が無い。直していない（ROADMAP の項目 24）（**v0.5.37 で解消**: root の分類を足した。範囲〈v0.5.37〉）
- （D グループ）**`package.json` が JSON としては正しいが形が違うとき**（`null`・配列・文字列・`scripts` が数値）: `null` と `scripts` が数値は生の TypeError で exit 2（`aiqh: unexpected error: …`）、配列と文字列は**空の `package.json` として Node プロジェクト扱い**（黙って受け入れる）。
  直していない（ROADMAP の項目 26）。併記: `src/adapters/types.ts` の `readText` の注記（「missing のとき null」）は、v0.5.31 までは実際の動作（読めないときも null）と合っていなかった。v0.5.32 で ENOENT 以外は例外になったので、その点は解消した（**v0.5.37 で解消**: 形が違うときも `ExaminationError`。範囲〈v0.5.37〉）
- （D グループ）**`exists()` は入口の種類を見ない**（lstat で「ある」かだけ）: `tests` が通常ファイルでも「tests/ directory present」と書く。直していない（ROADMAP の項目 27）（**v0.5.37 の訂正**: 実際の CLI では、`tests` が通常ファイルなら Python のアダプタが `tests/e2e` を調べた時点で ENOTDIR になり、決定 9 で `init` が止まる〈次の項目〉。「tests/ directory present と書く」は、アダプタを単体で呼んだときだけ起きる。残るのは `tests` が dangling symlink のとき〈推定〉。記録で閉じた）
- （D グループ）通常ファイルの下の入口（ENOTDIR）は「調べられない」なので、`tests` が通常ファイルの Python リポジトリや、`.venv` が通常ファイルのリポジトリでは `init` が止まる（決定 9。決定 4 と同じ扱い。人間の判断）。一覧できない root（0300）でも止まる
- （D グループ）root が辿れない（0600）とき、`init` のメッセージは最初に調べた入口の名前が出る（`cannot audit <root>: package.json cannot be examined (EACCES)`）。`describeRootProblem` は変えていない（人間の判断）
