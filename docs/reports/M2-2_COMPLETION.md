## 7. 学んだこと（波 3 の運用）

### 7.1 JSON の欄つきのひな形

- 波 3 の下調べ（SP1）で、それまでの 47 本のレビューの原文を読んだ。見出しの形を決まりにした依頼の後の 11 本でも、厳しく読めたのは 6 本。要約の欠け、同じ見出しの重なり、指摘でない ID の言及、前の回の ID の見出しなど、読み落としにつながる形があった
- そこで、依頼文のひな形（`docs/ops/review-request-template.md`）の最後に、**レビュアーの出力の形**（決まった欄の JSON のブロック）を足し、取り込みはその JSON を正本にして本文と突き合わせる形にした（ADR-0026）
- 結果: 波 3 の 5 回の原文は、どれも exit 0 で取り込めた。指摘の件数・ID・前の回の評価を、人が数え直さずに機械で照らせた

### 7.2 結果を受け取った後の指示書を先に用意する

- 人間は、レビューの結果が届く前に、結果を受け取った後の指示書（取り込み → 記録 → 単体検証 → push → CI → review-check）を用意した。指摘なし（場合 A: 記録して終える）と指摘あり（場合 B: 記録して直し方の案を出す）を分けて書いた
- 結果を受け取ってから、取り込みから CI までを 1 回の指示で進められた（m2-2-review-check R1 は場合 A、m2-2-parsers R1 は場合 B、R2 は場合 A）

### 7.3 指示書の取り違え 2 回（§1 の確認で止まって防げた）

- 2026-10-14: m2-2-parsers R1 の取り込みの指示書が、v0.8.0 を作る指示書より先に実行された。§1 の確認で v0.8.0 のタグも R1 の原文も無いことが分かり、何も変えずに止まった
- 2026-10-15: m2-2-parsers R2 の取り込みの指示書が、v0.8.1 を作る指示書より先に実行された。同じく §1 で v0.8.1 も R2 の原文も無いことが分かり、何も変えずに止まった
- どちらも、2 つの指示書が同じ時刻に保存されていた。§1 に HEAD・タグ・入力のファイルの確かめを書いておいたので、順序の取り違えが変更の前に止まった。以後も、指示書の §1 にはその指示の前提（HEAD・タグ・入力）を書く

### 7.4 負荷による時間切れの扱い

- 波 3 では、負荷のもとでだけ落ちる FAIL が 4 つの場面であった
  - v0.8.0 の各 commit の単体検証: 型を読むガードのテストの時間切れと、leader の準備の時間切れ。待ちの線を厳しくして（1 分平均 6 以下・5 分平均 8 以下）、3 回目に 5 commit とも PASS
  - v0.8.0 の HEAD の 10 回連続: 「線形の読みは時間の上限に届かない」を本物の時計で確かめるテストが 4 回目に FAIL。テストの確かめを、パーサが時計を見るたびに進む時計に替えた（`3648544`）
  - v0.8.1 のタグの後の self verify: 型を読むガードのテスト 5 件が 30 秒の時間切れ（直後の 15 分平均 91.53）。静かなときの 2 回目は PASSED
  - `e9c541d` の単体検証の 1 回目: 既存テストの前提の確認が FAIL（実行中の 1 分平均 82.03）。やり直しの 2 回目は PASSED。項目 41
- 扱い: 負荷の記録を残し、待ちの線を通ってから同じ commit をやり直す（回数を決めておく）。すべての回を報告に書く。時間の上限に届かないことを確かめるテストは、壁時計でなく、決まった進み方の時計で確かめる。前提がそろわないテストは、準備の順序を確かめる項目にする
